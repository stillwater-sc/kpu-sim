KPU Tile-Flow Debugger

Three hypothesized views of one run on a CPU + KPU SoC: the system-level schedule of tile movement, the lineage of tiles that meet in one compute tile, and a heat map of activity and energy on the floorplan. All three share one time cursor and one key: the naming-map resource that every event is recorded against.

syntheticNothing on this page is simulator output. The schedule is generated in the page so that the views can be judged before the record exists: 3 operators on an 8×8 checkerboard (32 L3 tiles, 32 compute tiles), an attached RV64 CPU, and four memory controllers. A hot spot and a misaligned operand are planted on purpose so that the diagnostics have something to find.

    Step 2 of 3

    Tile lineage: follow the tiles that meet in one compute tile

    Pick a compute. The view takes its backward causal slice: the descriptor that licensed each operand, the DMA, every buffer it sat in, and the wait before compute. A line is thick while resident, thin while in transit and dotted while waiting, and each wait is labelled with its cause.

    2b · Alignment at the CF

    taskopA in L1B in L1skewstart delaycause

    Skew = last operand arrival − first. Start delay = compute start − last arrival. A large skew means one operand sat in L1 waiting for its partner: the misalignment signal.

    Step 3 of 3

    Heat: activity, then energy, then temperature

    The S0 die view aggregated over a time window. Energy is attributed per event with the constants from characterize/device_model.hpp (20 pJ/byte moved, 1 pJ/MAC, 5 pJ leakage per tile per cycle). Thermal is a diffusion model over the floorplan and says so.

    For the review

    Decisions these views depend on

    Q1 · formatA columnar .tflow bundle (typed arrays + LOD pyramid), with Chrome trace kept as a derived export. This supersedes #286's "no new format" clause.
    Q2 · L3 at L-T1Today L3 is a pooled capacity. These slot pixels need the executor to bind each tile to a concrete L3 tile and slot. Until it does, the view draws one pooled station.
    Q3 · floorplan sourceGenerated from the deployment (shown here), or imported from the real SoC floorplan and validated against the naming map.
    Q4 · CPU detailOne block, or cores + SRAM + descriptor rings as separate blocks, so that MMIO traffic lands where it physically is.
    Q5 · viewer techPlain static HTML with Canvas2D/WebGL and no build step, as on this page.
    Q6 · color budgetThree operator hues validate together. Real models color by operator class and distinguish individual operators on hover.
