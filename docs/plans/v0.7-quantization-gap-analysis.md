# v0.7.0 Quantization Support: Gap Analysis

## Executive Summary

This document analyzes the requirements for v0.7.0 quantization support, compares available technologies, and recommends an implementation strategy that leverages the Universal arithmetic library while maintaining Python usability.

**Key Finding**: NumPy lacks native support for bfloat16, float8, and int4 types. The recommended approach is a **tiered implementation** that uses:
1. NumPy native types where available (float16, int8)
2. ml_dtypes extension for bfloat16/float8 in Python
3. Universal library via pybind11 for C++ timing simulation
4. Emulation with scale/zero-point for behavioral correctness

**IMPORTANT: Use Fast Types for BF16**

The fast `bfloat16` class (not `bfloat_t` from cfloat) should be used for BF16:
- Location: `include/sw/universal/number/bfloat16/bfloat16.hpp`
- Stores only upper 16 bits of float32
- Arithmetic: converts to float → native HW operation → converts back
- ~100x faster than cfloat emulation

```cpp
// CORRECT - use fast hardware-accelerated type
#include <sw/universal/number/bfloat16/bfloat16.hpp>
sw::universal::bfloat16 a = 1.5f;
sw::universal::bfloat16 b = 2.5f;
sw::universal::bfloat16 c = a * b;  // Uses native float hardware

// AVOID - slow emulated type (only for research/validation)
using bfloat_t = cfloat<16, 8, ...>;  // ~100x slower
```

**Capabilities:**
- Full arithmetic (+, -, *, /, sqrt, etc.)
- Conversions to/from float, double
- Numeric limits and traits
- Math library functions (exp, log, sin, cos, etc.)
- Tested and validated

### 3.3 Quantization Semantics

**Affine Quantization (INT8):**
```
x_quant = round(x_float / scale) + zero_point
x_dequant = (x_quant - zero_point) * scale
```

**Symmetric Quantization (INT8):**
```
x_quant = round(x_float / scale)
x_dequant = x_quant * scale
```

**Per-Tensor vs Per-Channel:**
- Per-tensor: Single scale/zero_point for entire tensor
- Per-channel: Scale/zero_point per output channel (better accuracy)

## 4. Implementation Options

### Option A: Pure Python Emulation

**Approach:** Store quantized values as int8/uint8 in NumPy, track scale/zero_point metadata, perform operations in float32 with quantization effects.

```python
class QuantizedTensor:
    def __init__(self, data: np.ndarray, scale: float, zero_point: int):
        self.data = data  # int8/uint8
        self.scale = scale
        self.zero_point = zero_point

    def dequantize(self) -> np.ndarray:
        return (self.data.astype(np.float32) - self.zero_point) * self.scale

    def matmul(self, other: 'QuantizedTensor') -> 'QuantizedTensor':
        # Dequantize → compute → requantize
        a = self.dequantize()
        b = other.dequantize()
        c = np.matmul(a, b)
        # Requantize with new scale
        ...
```

**Pros:**
- Pure Python, no dependencies
- Works with existing NumPy infrastructure
- Easy to debug

**Cons:**
- Doesn't capture true quantized arithmetic behavior
- No actual memory savings in behavioral mode
- Slow for large tensors

### Option B: ml_dtypes Integration

**Approach:** Use ml_dtypes for bfloat16/float8, which integrates with NumPy.

```python
import ml_dtypes
import numpy as np

# Register bfloat16 as numpy dtype
x = np.array([1.0, 2.0, 3.0], dtype=ml_dtypes.bfloat16)
y = np.array([4.0, 5.0, 6.0], dtype=ml_dtypes.bfloat16)
z = np.matmul(x, y)  # Works!
```

**Pros:**
- True bfloat16/float8 arithmetic
- Compatible with NumPy operations
- Used by JAX/TensorFlow

**Cons:**
- Additional dependency
- Limited to types ml_dtypes supports (no fp8e2, fp8e3, fp4)
- No int4 packed operations

### Option C: Universal via pybind11

**Approach:** Expose Universal types to Python via pybind11 bindings.

```cpp
// In kpu_native.cpp
#include <sw/universal/number/cfloat/cfloat.hpp>

namespace py = pybind11;
using bfloat16 = sw::universal::bfloat_t;

py::class_<bfloat16>(m, "bfloat16")
    .def(py::init<float>())
    .def("__float__", [](const bfloat16& x) { return float(x); })
    .def("__add__", [](const bfloat16& a, const bfloat16& b) { return a + b; })
    // ... etc
```

**Pros:**
- Full Universal capability exposed to Python
- Accurate arithmetic for all types
- Single source of truth (Universal)

**Cons:**
- Requires compiled bindings
- Scalar operations only (no vectorized NumPy)
- Performance overhead for many small operations

### Option D: Hybrid Tiered Approach (RECOMMENDED)

**Approach:** Use different strategies for different simulation fidelities.

| Fidelity | Strategy |
|----------|----------|
| BEHAVIORAL | Use PyTorch's quantized tensors or emulation for correctness |
| TRANSACTIONAL | Pass dtype info to C++ for memory traffic calculation |
| CYCLE_ACCURATE | Use Universal in C++ for accurate timing |

```python
# Python side (BEHAVIORAL)
@dataclass
class QuantizationConfig:
    dtype: str  # "int8", "fp16", "bf16", "fp8e4m3", etc.
    scale: Optional[float] = None
    zero_point: Optional[int] = None

def quantized_matmul(a, b, config: QuantizationConfig):
    if runtime.fidelity == BEHAVIORAL:
        # Use float32 with quantization noise injection
        if config.dtype.startswith("int"):
            return _emulated_int_matmul(a, b, config)
        elif config.dtype in ("fp16",):
            return np.matmul(a.astype(np.float16), b.astype(np.float16)).astype(np.float32)
        elif config.dtype == "bf16":
            # Use ml_dtypes if available, else emulate
            return _bf16_matmul(a, b)
    elif runtime.fidelity == TRANSACTIONAL:
        # Pass to C++ with dtype for memory traffic calculation
        return _native.quantized_matmul(a, b, config.dtype)
    else:
        # Full C++ execution with Universal types
        return _native.cycle_accurate_matmul(a, b, config.dtype)
```

**Pros:**
- Best of all approaches
- Matches multi-fidelity architecture
- Allows incremental implementation
- Uses Universal for accurate C++ simulation

**Cons:**
- More complex implementation
- Multiple code paths to maintain

3. **Implement INT8 emulation in Python**
   ```python
   def _numpy_quantized_matmul_int8(a, b, scale_a, zp_a, scale_b, zp_b, scale_out, zp_out):
       # Dequantize
       a_fp = (a.astype(np.int32) - zp_a) * scale_a
       b_fp = (b.astype(np.int32) - zp_b) * scale_b
       # Compute
       c_fp = np.matmul(a_fp, b_fp)
       # Requantize
       c_int = np.clip(np.round(c_fp / scale_out + zp_out), -128, 127).astype(np.int8)
       return c_int
   ```

   ```python
   def pack_int4(values):
       """Pack two int4 values into one byte."""
       low = values[::2] & 0x0F
       high = (values[1::2] & 0x0F) << 4
       return (low | high).astype(np.uint8)

   def unpack_int4(packed):
       """Unpack int4 values from packed bytes."""
       low = packed & 0x0F
       high = (packed >> 4) & 0x0F
   ```

## 6. Memory Traffic Calculation

For TRANSACTIONAL mode, calculate memory traffic based on dtype:

```python
def calculate_memory_traffic(op: DFXOp) -> int:
    dtype_bytes = {
        "fp32": 4, "fp16": 2, "bf16": 2,
        "fp8": 1, "int8": 1, "int4": 0.5,
        "fp4": 0.5
    }
    bytes_per_elem = dtype_bytes.get(op.quant_config.dtype, 4)

    if op.opcode == DFXOpCode.MATMUL:
        M, K, N = op.attrs["M"], op.attrs["K"], op.attrs["N"]
        # Read A (M*K), Read B (K*N), Write C (M*N)
        return int((M*K + K*N + M*N) * bytes_per_elem)
```

This enables 4x bandwidth reduction calculation for INT8 vs FP32.

## 9. Summary

| Aspect | Recommendation |
|--------|----------------|
| **INT8** | NumPy native + scale/zero_point |
| **FP16** | NumPy native |
| **BF16** | ml_dtypes |
| **FP8 e4m3/e5m2** | ml_dtypes |
| **FP8 e2/e3** | Python emulation, C++ Universal |
| **INT4** | Packed storage + emulation |
| **FP4** | C++ Universal only |
| **Memory traffic** | Calculate from dtype bytes |
| **C++ simulation** | Universal library for all types |

The key insight is that **behavioral correctness** can be achieved with emulation, while **accurate timing simulation** requires the C++ Universal library. This matches the multi-fidelity philosophy of the KPU simulator.
