## 1. Summary

The RTL generator reads an embodied-schemas KPUArchitecture; kpu-sim reads a DeploymentSpec.
Nothing mapped one onto the other. Now:
- `tools/deploy/kpuarch_to_deployment.py` converts the generator's expanded config;
- `DeploymentSpec` has a `systolic` block for what the RTL tile is built with;
- `tests/program/deploy/kpu_soc_2x2.json` is one tile of `kpu_2x2_systolic`, kept in step with a
  vendored copy of the generator's config;
- an int8 program runs on it at L-B, L-T1 and L-CA, with L-B's values word for word.

## 3. Technical Decisions

- **Decision 1: the converter is Python, on the generator's format.** kpu-sim has no YAML library.
  The converter reads the expanded YAML, or JSON, and writes canonical DeploymentSpec JSON,
  which kpu-sim's reader then checks strictly. The research found the generator's side already
  has pydantic and the schemas. This converter needs neither: it reads the expanded spec as data.
- **Decision 2: the slots, banks and latencies come from kpugen's code.** They are not
  KPUArchitecture fields. `SystolicConfig`'s defaults and `tile.py`'s constants set them, so the
  converter holds them in `GENERATOR_DEFAULTS`, pinned to the kpugen revision they were read
  from, and lists them in its notes as defaulted.
- **Decision 3: "refuse instead of drop".** An unknown field, or a value the converter cannot
  represent, is refused. A known field with no counterpart is carried as "not carried" with its
  reason: energy, kernel lists, labels, and the 2x2 grid in single-tile mode. Nothing is dropped
  silently, and the notes are checked in.
- **Decision 4: the generator's DRAM is not carried.** One LPDDR5 controller on a 64-bit bus is
  4 x16 channels; kpu-sim's LPDDR5 controller drives 1 or 2. Inventing a second controller would
  misstate the machine. The DRAM block is left out, said so in the notes, and kpu-sim's built-in
  memory timing stands in.
- **Decision 5: tiles are counted in the accumulator's width.** The L3 capacity in tiles is
  64 KiB / (4 × 4 int32 = 64 B) = 1024.

## 4. Issues Encountered

- **The 2x2 config's tile is weight-stationary.** #397's tile command stream (version 1) lowers
  output-stationary programs, and kpugen's OS build is a separate cocotb target. The deployment
  carries `weight_stationary` as the generator states it. Running #397's stream on this tile
  needs the OS build or a WS lowering.
- The first version of the run test compared int32 results as floats; NaN bit patterns made
  equal words compare unequal. It now compares words.
- kpu-sim's DRAM technologies are lpddr5, lpddr5x, ddr5, hbm2, hbm3, gddr6 and gddr7. The
  converter's table matches them.

- **Review (CodeRabbit, PR #422), four findings, all valid:**
  - Floating-point MAC formats mapped to integer widths: an fp16 -> fp32 tile read as int16 ->
    int32. Refused until DeploymentSpec has a format field.
  - int4 wrote `element_bytes: 0`, which kpu-sim's reader refuses. Refused until a packing
    contract exists.
  - YAML and JSON loaders keep a duplicated key's last value silently. The converter's loaders
    now refuse a duplicate.
  - Two memory controllers with the default single DMA engine made a deployment kpu-sim's
    validation refuses. The converter writes one engine per controller, named in the notes.
  Each has a test that fails on the old converter.
