## 3. Technical Decisions

**Decision 1: grade examples by evidence, against ADR 0001 D6**
- **Choice:** For each example I checked its `#include`s against the engine dispositions in
  ADR 0001 D6 and #266, ran it (C/C++ with a 60 s limit, Python with 120 s), checked whether it
  checks values, and grepped it for cache vocabulary. Each verdict carries reason codes
  (F frozen, T timing only, B broken, C cache terms, O orphan).
- **Alternatives considered:** grading by git dates. Rejected: the June–July 2026 dates mostly
  come from repo-wide mechanical commits (include restructuring, `-Werror`, the Combiner rename).
- **Rationale:** a "last touched" date doesn't show that an example was maintained, and an
  exit code doesn't show that it is correct.
- **Files:** `docs/analysis/examples-inventory.md`

**Decision 2: frozen-engine examples retire with their engines, not ahead of them**
- **Choice:** #500 adds the remaining dependents to #266's lists, per engine, and keeps #266's
  "delete at parity" rule.
- **Rationale:** ADR 0001 §7.2. The silently wrong examples are split out into #497, because they
  mislead readers today.

**Decision 3: milestone v1.0.0 for all seven issues**
- **Choice:** v1.0.0, where the other `area: hygiene` issues (#266 among them) are.
- **Alternatives considered:** v0.10.0 for #497 and #498. I told the user it is available.

**Decision 4: answer CodeRabbit's last #496 follow-up with a run, not a code change**
- **Choice:** CodeRabbit raised a late store nested in a `stage` block that the validator doesn't
  carry into the next iteration. I ran its program through the walker: at `l2 = 3` it is refused
  with `csp line 10: … all 3 are held`, and at `l2 = 4` it is accepted, with values within bound
  of L-B. I replied with this on the thread.
- **Rationale:** the case is the class `f1e9e7f` was written for: the walker is the authority
  for L2 capacity and the validator a lower bound, so one exact model is the authority instead of
  two that must agree.

## 4. Issues Encountered

- **The PR #496 loop stalled.** *Symptom:* `pr-watch.sh` kept reporting `CR_AVAILABLE`, and
  `@coderabbitai review` answered "Already reviewed the last commit". *Root cause:* a clean
  incremental CodeRabbit review posts no `pulls/N/reviews` entry. It only updates the summary
  comment ("between `99b2f82` and `f1e9e7f`") and the CodeRabbit check run. The watcher keys on
  a review whose `commit_id` is the head. *Fix:* I checked those two signals by hand, and recorded
  the check as a memory for future loops. `pr-watch.sh` itself is not changed yet.
- **`gh pr merge --delete-branch` couldn't delete the local branch**, because a previous
  session's worktree under `/tmp` still claimed it after its directory was gone. `git worktree
  prune` cleared it.
- **The examples sweep found failures** (they are reported, not fixed, in this session):
  `basic/data_movement_pipeline` aborts (#498). `compiler/l3_comprehensive_analysis`,
  `l3_focused_analysis` and `l3_transformer_analysis` time out (#501). Four examples exit 0 on
  wrong results (#497). 11 `examples/python` scripts and `torch/model_compatibility.py` fail
  (#502).

## 5. Wrong Decisions

- **I trusted the watcher's model of "reviewed".** When I picked up #496, I saw no review on
  `f1e9e7f` and posted a review request without first reading CodeRabbit's summary comment and
  check run, which already showed the head reviewed. The user then had to ask whether to merge by
  hand. *Lesson:* when the watcher waits on CodeRabbit, check the summary's covered range and the
  check run first. Also look for a CodeRabbit reply posted after my last reply, which can carry an
  open follow-up, as one did here. Recorded as the memory `cr-silent-clean-review`.
- **The first report draft miscounted its summary** (14 current and 41 outdated; the true counts
  are 16 and 42). I caught it by recounting the tables against `git ls-files` before reporting.
