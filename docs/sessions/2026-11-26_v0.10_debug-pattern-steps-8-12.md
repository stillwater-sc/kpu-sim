## 3. Technical Decisions

**Decision 1: one data layer for the four DRAM views.**
- **Choice:** `tools/visualization/common/dram.js` derives banks, bank states, each burst's command
  chain and its timing gaps from the record, in controller ticks. Every view draws from it.
- **Alternatives considered:** each view computing its own (the old Chrome-trace views did).
- **Rationale:** the views must agree with each other and with `mflow_check.py`. `gaps()` mirrors
  M5's rules: tRP from the bank's last PRE and tRFCpb from its last REF, each on its own.

**Decision 2: the patterns record through the controller's command observer.**
- **Choice:** the harness wraps submits and observes commands; source `lpddr5-pattern`, no engine
  (`NONE`), one tick per cycle, the ceiling in the manifest.
- **Consequence:** M1 allows a record with no `dma` station to have bursts of no engine. The cycle
  core's records still need an engine.

**Decision 3: the cycle demos keep no external DRAM check.**
- **Choice:** `cycle_dram_demo`, `cycle_l3_dma_demo` and `cycle_csp_l3_demo` write only their core
  trace and counters.
- **Alternatives considered:** wiring an `MflowRecorder` into each demo's rig.
- **Rationale:** their channel checks the controller's timing invariants as it runs and throws on a
  violation. The cycle core's DRAM side is checked by `mflow_check.py` on `cycle_mflow_s1/t4` and on
  kpu-run's `memory_s1` run, which now records `.mflow` (`kpu_run_memory_mflow_check`).

**Decision 4: a Chrome trace is a trace.**
- **Choice:** the debug server drops its `dram-trace` kind. Every Chrome trace opens in Perfetto.
- **Rationale:** no LPDDR5 DRAM trace is written any more; sniffing for "LPDDR5" served nothing.

**Decision 5: the MCP tool's `all` skips the self-tests' fixtures.**
- **Choice:** `kpu_validate_trace("all")` checks `build/patterns/`, `traces/` and `runs/`.
- **Rationale:** the self-tests leave deliberately broken copies under `build/tests/`. Checking
  them reported 40 violations that are the tests working.

**Decision 6: stacked work, cherry-picked onto main.**
- **Choice:** with reviews rate-limited, the next steps were prepared locally on top of the open PR.
  Once it merged, the step's own commit was cherry-picked onto the new main.
- **Rationale:** there was no rebase or force-push of a pushed branch. A pushed branch took main by
  merge (#590 after #589).

## 4. Wrong Decisions and Mistakes

1. **An unquoted heredoc ran backticks as commands** and corrupted a draft `dram.js`. The draft was
   restored from a backup. **Lesson:** quote heredocs (`<<'EOF'`), or write a script file.
2. **A stall test passed without its fix**: the client's response object was garbage-collected,
   which closed the socket. **Lesson:** run every regression test against the unfixed code. This
   test only failed once the response object was kept alive.
3. **A pattern bundle looked wrong after a mutation run**: it was stale, written by the mutated
   binary. **Lesson:** re-run the producer after restoring a mutation.
4. **9d's test expectations were wrong** (the buffer sample time and engine 1's state). The code
   was right. **Lesson:** derive expectations from the fixture's numbers, not from memory.
5. **A review "from CodeRabbit" was my own reply**: GitHub files replies as reviews. **Lesson:**
   check the reviewer's login.
6. **9c's debug-server README lost an "and" and two commas** when the sentence was extended. It was
   fixed before review.
7. **9d's `pack.py` did not list the block diagram.** `dram_views_t4` caught it on the first run.
8. **Two review requests a few minutes apart**: the second (#590) was refused as rate limited.
   **Lesson:** one request per free slot.
9. **The guide's first draft claimed** that a view reloads itself on a re-run (it offers a Reload
   button) and that every view takes a `t=` link (the DRAM views do; the memory-side debugger
   does not). Both were checked against the code and corrected before the commit.
