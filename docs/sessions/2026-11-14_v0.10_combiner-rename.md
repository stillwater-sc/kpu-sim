# Session 2026-11-14: the Vector Engine is the Combiner (#429, the rename)

## Context

The order agreed for v0.10.0 is #429 (the Combiner: rename and merge of partials), then #427
(the rest of the Combiner), then #425 (the CSP data-movement viewer). The viewer must see the
Combiner's L2 traffic, so it comes last. This session filed #430 (WS and IS matmul programs for
`kpu-csp-gen`, which #429's tests need), put #427, #429 and #430 in v0.10.0, and did the first
of #429's two PRs: the rename, with the old spellings kept as deprecated aliases.

## Finding: the CSP levels never used the Vector Engine class

`VectorEngine` (models/temporal) is used by the ISA / kpuasm path only. The CSP program's L1 -> L2
fusion site is the place `@ str.drain`, timed on each streamer's drain from the deployment's
`movers.vector.str` (`docs/plans/csp-language.md` said: "`VectorEngine` timing model exists,
unused"). Renaming the class alone would leave the Combiner unnamed where L-B, L-T1 and L-CA
execute programs, and the merge of partials has to land on that site.

**Decision (asked, 2026-11-14):** rename the CSP side too. `@ str.drain` -> `@ combiner`, and
`movers.vector.str` -> a top-level `combiner` block in the device spec, both with deprecated
aliases. `bm.egress` (L2 -> L3) stays a separate vector site.

## What changed

- C++: `VectorEngine*`, `VEOperation`, `VEStats`, `BehavioralVectorEngine` -> `Combiner*`; the
  ISA's `VE*` types -> `CMB*`; `ResourceType::VECTOR_ENGINE` -> `COMBINER`; files renamed.
- ISA: `VE_ELEMENTWISE` / `VE_REDUCE` -> `CMB_*` (opcode values unchanged), drain fields
  `ve_*` -> `cmb_*`, kpuasm `VE_ENABLE` -> `CMB_ENABLE`.
- CSP: `Place::StrDrain` -> `Place::Combiner` ("combiner"); `Target::str` -> `Target::combiner`;
  timing `str_ve_lanes/rate` -> `combiner_lanes/rate`, `VectorStats::str_*` -> `combiner_*`;
  kpu-run prints `combiner`.
- Deployment: `DeviceSpecification::combiner`; the reader takes `combiner` or the deprecated
  `movers.vector.str` (same digest), refuses both together; the writer emits `combiner`.
- Kept as they were: the generic per-site counters (`ve_cycles`, `ve_busy_cycles`) shared by the
  Combiner and the BlockMover's vector unit, and `bm_ve_*`. Session logs, archived docs,
  point-in-time assessments and the coverage manifests' history notes keep the old name.

## Aliases, each tested

- `.kpuasm` with `VE_*` mnemonics assembles to the same binary as with `CMB_*`.
- Program JSON with `ve_*` drain keys loads to the same program.
- `@ str.drain` compiles to the same program (printed as `@ combiner`) with the same L-B values.
- `movers.vector.str` reads as `combiner` with the same digest and writes back as `combiner`.

## Wrong decisions

- My first JSON-alias test rewrote every `"cmb_` in the text, including the test program's own
  name `"cmb_json"`, so the two binaries differed. Fixed the test data (the code was right);
  lesson: a textual rewrite in a test must not be able to match the fixture's own strings.
- I missed `Target::str` in `tests/program/test_csp_gen.cpp`; the gcc build caught it.
