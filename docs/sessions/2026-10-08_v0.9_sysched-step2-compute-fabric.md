# v0.9 System-Schedule Debugger Step 2: The Compute Fabric and kpu_s1

**Date:** 2026-10-08
**Version:** v0.9
**Status:** Complete (step 2); step 3 (the schedule dispatcher, prefetch depth P) next
**Tests:** test_csp_spec_oracle (values on S1, T4, T16, T64; the fabric); full suite in the PR

## 1. Summary

Before this step, a compute in the CSP executor was a list entry. Any number ran at once, for a
fixed `32 + 32·(k-1)` cycles, and the spec's `compute_tiles` and `macs_per_cycle` were ignored.
- Compute tiles are now resources: one compute at a time each, for as long as their MACs take at
  the spec's rate.
- `kpu_s1` is the machine the architect asked for: one large L3 and one large compute fabric, the
  T4's resources folded into one site.

## 2. Decisions

- **The legacy model stays the default for hand-built configs.** `num_compute_tiles = 0` keeps
  every existing hand-built executor test unchanged. Spec-driven runs (`csp_config_from`) get the
  fabric.
- **`cf_tile` lives on `TileDescriptor`, not `ScheduleOperation`.** The executor's four compute
  overloads take a descriptor. The descriptor already carries the other placement decision,
  `l3_tile`.
- **K comes from the inputs as fed.** The executor sees TileIDs at compute time, so each fed
  tile's shape is remembered at `schedule_feed`. The generator's tiles are all `Ti x Tj`
  (square in practice), which makes K exact today. A non-square schedule needs the generator
  fixed first; that is noted, not done.
- **An unnamed compute takes the first free tile.** The plan said "least-loaded". With one
  compute at a time, first-free is the same decision made when it matters, at start.

## 3. Observations

- Matmul 128³ with 32³ tiles: S1 runs 9,836 cycles, against the T4's 9,549, T16's 5,084 and
  T64's 3,796.
- Twice the MACs per tile buys nothing: the run is memory-bound, as the plan's §1 balance
  predicts.
- S1's `single` layout also has one BlockMover against the T4's four. Step 4's record will say
  which limit binds.

## 4. Wrong Decisions

- **I first ran the oracle binary from the build directory.** The fixtures are read relative to
  the repository root, so the runs failed. Use ctest, which sets the working directory. No code
  was affected.
