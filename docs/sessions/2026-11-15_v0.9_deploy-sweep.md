# v0.9 kpu-run: a Sweep over Deployments (#285)

**Date:** 2026-11-15
**Version:** v0.9
**Status:** in review (draft PR). #285 stays open: stepping at L-CA is the next PR, and L-T2 is
#283's.
**Tests:** see §6.

## 1. Summary

v0.9.0 has two open issues, #285 and #397. kpu-sim's half of #397 shipped in #421. #285's done
criteria still missing were:
- a sweep over deployments;
- `--step` at L-CA;
- all four levels, which needs L-T2 (#283, v0.11.0).

This PR adds the sweep. Running the same program on several machines is how a deployment is
chosen, and the driver could only run one at a time.

The user also corrected how the docs relate kpu-sim to the RTL. kpu-sim is the architecture
simulator, and the RTL generator implements what kpu-sim has shown to work. The Combiner's docs
had described its order of operations and its rounding mode as esg#68's, to be followed. They now
describe them as the architecture's, which the RTL implements.

## 3. Technical Decisions

- **Decision 1: the sweep is `--deploy` repeated**, not a comma list or a directory.
  - Rationale: it is unambiguous for any path, and the flag keeps its meaning.
  - `arg_required` reads only the first occurrence. That is why an L0 program used to accept two
    `--deploy` flags and silently run the first. It now refuses them.
- **Decision 2: each deployment has its own platform and its own oracle.** Validation depends on
  the target, so a deployment can refuse the program. Its row says so, and the sweep exits 2.
  Every level is checked against that deployment's L-B.
- **Decision 3: L-B is checked across deployments bit for bit.** L-B does the same computation
  on every machine, which is the case where CLAUDE.md sets bit equality as the bar. A difference
  is a kpu-sim defect (exit 1).
- **Decision 4: what records one run is refused, not written for the first deployment.** This
  covers `--tflow`, `--dflow`, `--timeline`, `--tile-commands`, `--emit-l0*` and `--step`. A
  per-deployment file naming scheme can come later if a use appears. `--bubbles` is allowed and
  prints once per deployment, because comparing where the lanes wait is what a sweep is for.
- **Decision 5: a level a deployment cannot run is skipped on that row, with its reason.** A
  named level is not a usage error in a sweep, unlike a single run. The sweep exits 2 only when
  nothing ran on a deployment.
- **Decision 6: a refactor first.** The level printout and the value check moved into
  `print_levels` and `print_value_check`, so the single run and the sweep share them.

## 4. Issues Encountered

- **The extraction missed one use of `authority`** in `--emit-l0-result`. gcc caught it, and it
  now reads `res.reference`.
- **The build waited on itself.** I had queued it behind another session's Universal build. The
  wait loop used `pgrep -f cc1plus`, and its own command line contains "cc1plus", so it could
  never stop waiting. Meanwhile the machine (20 cores) sat at a load below 1. The user asked for
  resources to be managed dynamically. Builds now size `-j` from the live load (4 to 16) and wait
  on process names (`pgrep -x`), never on a pattern their own command line matches.

- **Review (CodeRabbit, PR #439): two findings, both valid.**
  - A sweep with `--bubbles` that made no L-T1 run (`--level behavioral`) printed no report and
    still exited 0. The single run refuses that combination. Now:
    - the sweep refuses it up front, with the same reason;
    - a deployment on which L-T1 was skipped makes the sweep exit 2.
    - Test: `kpu_run_csp_sweep_bubbles_needs_lt1`.
  - The Combiner's order was not enforced for a bias. The resolver refused a scale after an
    activation but accepted `relu, add(b[j])`, a bias after the activation it should feed. This
    check predates this PR; the PR's rewording of the comment brought it into view.
    - An add after an activation or format is now refused.
    - The check runs after the places are checked, so a program listed out of place order still
      gets that error first.
    - Tests in `test_csp_linear`: the misordered pair at one place, and at two places.

## 5. Wrong Decisions

- **Framing kpu-sim as following the RTL.** Earlier docs, comments and my status reports did
  this. Examples: the Combiner's order was called "esg#68's order", the rounding mode was a
  "provisional choice, to follow the RTL", and #427 part 3 was described as "blocked" on esg#67
  and esg#68. All of these are reworded. Lesson: kpu-sim decides the architecture, and the RTL's
  issues are where it gets implemented.
- **A fixed `-j4`, one build at a time, on an idle 20-core machine.** That wasted the machine.
  The rule came from an earlier load-400 incident, but the fix for that is to size builds to the
  load, not a fixed cap.

## 6. Verification

```bash
build/tools/kpu-run/kpu-run --program tests/program/corpus/matmul_48x48x48_t16.csp \
    --deploy tests/program/deploy/kpu_s1.json --deploy tests/program/deploy/kpu_t4.json
(cd build && ctest -R "kpu_run_csp_sweep|kpu_run_l0_refuses_sweep" && tests/program/test_driver_run_at)
```

In the two-deployment run, L-CA runs on S1 (1948 cycles) and is skipped on T4, whose level-2
placement distributes. L-T1 takes 1366 cycles on S1 and 529 on T4. L-B is bit-identical on both.
