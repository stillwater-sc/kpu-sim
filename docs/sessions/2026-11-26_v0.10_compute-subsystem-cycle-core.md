# v0.10 The compute subsystem on the cycle core (Phase 2, steps 2a–2f) Decision Log

**Date:** 2026-11-26
**Version:** v0.10
**Status:** Complete
**Tests:** 499/499 (gcc), 493/493 (clang)

## 1. Summary

Phase 2 of `docs/plans/cycle-based-kpu-prototype.md` is built. The compute subsystem runs from a CSP
program on the cycle core, from L3 to L3:

```
L3 -> BlockMover -> L2 -> Streamer -> L1 lanes -> PE array -> north FIFOs -> Combiner -> L2 -> BlockMover -> L3
```

C in L3 equals L-B's per tile, int32 exact, and every rule is built as state, from the RTL
(embodied-ai-soc-generator `b57c881`).

`kpu-run --compute-subsystem` prints the counters summary, writes a Perfetto trace with lanes per
L1 buffer, PE row, FIFO, L2 bank and slot, and writes an array utilization heatmap.

## 3. Technical Decisions

**Decision 1: the L3 is loaded in the L2's lane layout (2e).**
- **Choice:** an A tile is a row per lane, and a B tile a row per column (transposed), each padded
  to the L2's row.
- **Alternatives:** build the transform from Phase 1's dense row-major packing into the
  BlockMover's write path.
- **Rationale:** the transform belongs on the BlockMover's write into L2 (memory-hierarchy-roles),
  but it is a hardware decision (a tile buffer for the transpose) beyond one component's PR. The
  plan allows "the same state loaded directly".
- **Open:** the join (step 3) must build it.

**Decision 2: each L3 slot holds one residency over the run (2e).** A program that reuses a slot is
refused, since running its Loads in time is the join's work. The 64³ runs with `l3 = 96`.

**Decision 3: a chain ends at its last call (2e).** The RTL's `last` launches results north at
once. A Drain the walker defers (`store … late`) is the same L2 Result, in program order.

**Decision 4: a call needs A and B in two L2 slots (2e).** The Streamer reads both operands' rows
in the same clocks, while the CSP feeds each tile into L1 whole. So `l2 = 2`, and `l2 = 3` with
late stores, are refused with a message naming the action.

**Decision 5: PE-clocks are counted by cause in the array (2f).** The causes are useful, padded,
draining and waiting on L1. That each PE's causes add to its clocks is checked as a law.

**Decision 6: one machine (2f).** `ComputeMachine` and the stand-in L3 moved from the tests into the
library, so kpu-run and the tests build the same model. `check_laws` moved to `report.hpp`, shared
by both subsystems.

**Decision 7: the default mover beat is 64 bytes (2f), step 2a's default.** At 16 bytes the 64³
takes 10020 clocks, against 5632.

## 4. Issues Encountered

- **The generated 64³ was refused.** The planner refused it ("a chain opens while another is in the
  fabric"). The cause was `store … late` placing a Drain after the next chain's first call. Fixed by
  Decision 3.
- **The walker put A and B in one L2 slot.** This happened with single buffering and late stores;
  the Streamer refused it. The planner now refuses it first, with a CSP-level message (Decision 4).
- **MSVC C1128 on `test_cycle_compute_subsystem`.** Fixed with `/bigobj`, as the memory test
  already has.
- **CodeRabbit's five findings on #597**, each fixed with a regression test that fails without the
  fix:
  - a zero mover beat was SIGFPE;
  - the trace and heatmap writers checked the stream before closing it, so a flush failure went
    unreported (tested on `/dev/full`);
  - two `--compute-*` artifacts could name one file;
  - `check_run_dir.py` raised on a non-string kind or a malformed heatmap.
- **CodeRabbit's sixth finding on #597, from its second review.** `test_check_run_dir.py MEMORY_DIR -v`
  took `-v` as the compute directory. The compute cases now skip by the parsed directory, and a
  CTest runs that form.
- **Reviews.** The last review of #597 was a paid on-demand one ($0.50). The user's rule for this
  case: wait when the free review is within 15 minutes, otherwise pay (it was 53 minutes away).

## 5. Wrong Decisions

- **The first draining check was weak.** The first 2f test checked only `draining > 0`, so a
  mutation that misclassified draining was caught by one assertion only. Corrected with exact
  counts: PE(0,0) has 16·15 draining clocks and PE(15,0) none.
  - **Lesson:** a counter's test states the value the program implies.
- **The first `kpu-run` default beat was 16 bytes,** which halved the throughput reported against
  2a's own default. It was caught by comparing with the 2e test's figure before the PR.
  - **Lesson:** compare a new entry point's numbers against the tests' runs of the same program.

## 6. Verification

```bash
cmake --build build -j16 && (cd build && ctest -L compute --output-on-failure)
./build/tools/csp-gen/kpu-csp-gen --algo matmul --size 64 --tile 16 --dtype int8 --l3 96 \
    --target tests/program/deploy/kpu_s1.json -o /tmp/mm64c.csp
./build/tools/kpu-run/kpu-run --program /tmp/mm64c.csp --deploy tests/program/deploy/kpu_s1.json \
    --compute-subsystem --run-dir build/runs/mm64c
python3 tools/kpu-run/check_run_dir.py build/runs/mm64c --status ok
python3 tests/cycle/check_trace.py build/runs/mm64c/trace.json build/runs/mm64c/counters.json
```

Measured on the int8 64³ on kpu_s1:
- 5632 clocks, 0.57% array utilization;
- the BlockMover busy 80% of the run;
- each L2 bank 1.64 reads in flight on average, 8 at most.
