## 1. Summary

An operand declares its number system, and a gemm computes in it:

```
tensor A[8,8] int8 tile 4x4 in;
tensor B[8,8] int8 tile 4x4 in;
tensor C[8,8] int32 tile 4x4 out;     // int8 x int8 summed in int32, wrapping at 32 bits
```

The arithmetic is stillwater-sc/universal's. kpu-sim already fetched Universal at v3.91, but
only `quantization/` used it.
- A compiled registry (`src/program/numeric.cpp`, the one file that includes Universal) maps a
  universal_dtypes name to its Universal type.
- It also maps a gemm's (input, accumulator) pair to a MAC instantiated for those types.
- L-B, the L0 replay and L-T1 call the same kernels, so they compute the same bits.

## 3. Technical Decisions

- **Decision 1: number systems from Universal** (the user, 2026-11-11). The user asked why kpu-sim
  wasn't using stillwater-sc/universal: it is a simulator for experimenting with custom
  arithmetic. The first proposal was a hard-coded int8/int32 path. The design now carries a
  number system, so adding bfloat16, fp8 or a posit is one registry row.
- **Decision 2: 32-bit words** (the user's choice). An element keeps its 4-byte slot. fp32 stores
  the float; another type stores its Universal bit pattern, zero-extended. Code that moves tiles
  is unchanged.
  - The word accessors `memcpy`, so a word never passes through a float register.
  - The cost: formats wider than 32 bits (posit64, the cascades, a quire) wait for a typed
    element buffer.
  - Rejected: the typed buffer now (about 200 sites), and double storage.
- **Decision 3: the registry is compiled once, in `kpu_program`.** Universal's headers stay out of
  the about 24 headers that include the tile program. Every level reaches the MAC through a
  function pointer.
- **Decision 4: the accumulator's type is the result operand's.** A gemm's inputs share one number
  system, and `(in, C's type)` must be registered. alpha must be 1 for a typed gemm. An init is
  in the accumulator's number system. Every non-gemm kernel and every tile context (`via`)
  computes in fp32 and refuses a typed operand by name.
- **Decision 5: the type is a container attribute, not an op.** A 1.2.0 L0 reader would ignore
  `type=` and read the words as floats, which is a silent wrong answer. So a typed file says
  `KPUL0 1.3.0` and `MIN_CONSUMER 1.3.0`, by the rule the header already states. fp32 files keep
  1.2.0, so the corpus is byte-identical. The plan's first draft said "opset 1.5"; that was
  corrected.
- **Decision 6: integers are checked exactly.** `tile_check` ignores the caller's bound for an
  integer system. Integer arithmetic has no rounding to forgive.
- **Decision 7: L-T1 runs typed programs in step 1.** It takes its values from L-B's
  interpreter. The plan had it refused until step 2.

## 4. Issues Encountered

- My first wrap test counted wraps among random int32 C values and found none. Eight products of
  at most 2^14 rarely carry a random int32 past ±2^31. It now builds the inputs: C near INT32_MAX
  and A = B = 127, so every element wraps. The MAC's own unit test covers the wrap too.
- `DomainFlowRecorder` refuses in its constructor. The test first called a `begin` that doesn't exist.
- `kpu-run` printed "float32 within 1e-6 + 1e-4|o|" for an int32 result. It now names each
  operand's bound ("int32 exact").

## 5. Wrong Decisions

- **The first #394 design hard-coded int8 and int32**, beside a kpu-sim that already depended on
  Universal. The user pointed out that the simulator is for experimenting with arithmetic.
  **Lesson:** before adding a numeric type, look for the number-system library the project
  already has (Universal is stillwater-sc's own), and design for a type parameter, not a type.
