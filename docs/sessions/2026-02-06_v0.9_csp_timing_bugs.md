# v0.9 CSP Timing Model Bug Fixes

**Date:** 2026-02-06
**Version:** v0.9.0
**Status:** Complete
**Tests:** 80/80 passing (concurrent timing executor tests)

## 1. Summary

Fixed two critical bugs in the CSP concurrent timing model that caused incorrect trace visualization:
1. DMA channels issuing 8 concurrent transfers instead of 1
2. DRAIN operations starting at cycle 0 instead of waiting for computation to complete

## 2. Scope

| Issue | Status | Root Cause |
|-------|--------|------------|
| DMA 8 concurrent transfers | FIXED | `in_flight_.size() < config_.queue_depth` allowed 8 in-flight |
| BlockMover at cycle 0 | NOT A BUG | BM_STALL_TAG events (stalls), not actual transfers |
| DRAIN at cycle 0 | FIXED | No compute dependency tracking |

## 3. Technical Decisions

### Decision 1: DMA Single Transfer per Channel

**Choice:** Changed from `in_flight_.size() < config_.queue_depth` to `in_flight_.empty()`

**Rationale:** A DMA channel represents a single physical channel to memory. It can only
perform one transfer at a time. The `queue_depth` parameter should limit pending requests
in the queue, not concurrent in-flight transfers.

**Files:** `include/sw/kpu/timing/dma_engine_process.hpp`

### Decision 2: COMPUTE Operation for Dependency Tracking

**Choice:** Add COMPUTE schedule operation type that signals when computation completes

**Alternatives Considered:**
- Track all FEED completions and auto-trigger compute (complex dependency tracking)
- Fixed latency from schedule start (doesn't model actual dataflow)
- DRAIN waits for last FEED (requires knowing which FEED is "last")

**Rationale:** COMPUTE is scheduled after all FEEDs for a C tile. It specifies a
dependency tile (last B tile for that column). COMPUTE only starts when the dependency
is FED, then adds compute latency. DRAIN waits for the result in compute_result_tag_cam.

**Implementation:**
- Added `compute_result_tag_cam_` to ConcurrentTimingExecutor
- Added `fed_tiles_` set to track tiles that have been FED to compute
- Added `PendingCompute` struct with dependency_tile and started flag
- COMPUTE starts when dependency_tile appears in fed_tiles_
- After compute_latency cycles, result inserted into compute_result_tag_cam
- DRAIN checks compute_result_tag_cam before proceeding

**Files:**
- `include/sw/kpu/timing/concurrent_timing_executor.hpp`
- `include/sw/kpu/timing/streamer_process.hpp`
- `include/sw/kpu/timing/schedule/schedule_generator_interface.hpp`
- `include/sw/kpu/timing/schedule/schedule_executor.hpp`
- `include/sw/kpu/timing/schedule/matmul_schedule_generator.hpp`
- `include/sw/kpu/timing/process_interface.hpp`

## 4. Issues Encountered

### Issue 1: DMA 8 Concurrent Transfers

**Symptom:** Trace showed 8 DMA_LOAD_START events at cycle 0 per DMA channel

**Root Cause:** `try_issue_loads()` condition was:
```cpp
while (!load_queue_.empty() && in_flight_.size() < config_.queue_depth)
```
With `queue_depth=8`, this allowed 8 concurrent in-flight transfers.

**Fix:**
```cpp
while (!load_queue_.empty() && in_flight_.empty())
```
Now only 1 transfer at a time per channel.

### Issue 2: DRAIN at Cycle 0 (No Compute Dependency)

**Symptom:** STR_DRAIN_START events at cycle 0, before any tiles were fed

**Root Cause:** `try_start_drain()` only checked L2 credits:
```cpp
if (!l2_credits_.acquire()) { ... }
```
No check for whether computation had completed.

**Fix:** DRAIN now waits for compute_result_tag_cam:
```cpp
auto compute_entry = compute_result_tag_cam_.match(tile.tile_id);
if (!compute_entry.has_value()) {
    events.push_back(TimingEvent(EventType::STR_STALL_COMPUTE, ...));
    stall_cycles_compute_++;
    return false;
}
```

### Issue 3: COMPUTE_START at Cycle 0

**Symptom:** After adding COMPUTE, all COMPUTE_START events were at cycle 0

**Root Cause:** `schedule_compute()` was called at cycle 0 during initial enqueuing.
Compute timer started immediately regardless of whether inputs were ready.

**Fix:** Added dependency tracking:
- COMPUTE specifies a dependency_tile (last B tile for that C output)
- PendingCompute tracks whether compute has started
- In step(), check if dependency_tile is in fed_tiles_ before starting timer
- Only emit COMPUTE_START when dependency is satisfied

## 7. Key Learnings

1. **DMA channels are physical resources** - They can only do one transfer at a time.
   Queue depth limits buffered requests, not concurrency.

2. **Schedule enqueuing happens before simulation** - Operations are enqueued at
   cycle 0, so any time-dependent logic must happen during step(), not scheduling.

3. **Compute is implicit in dataflow** - There was no explicit compute modeling.
   DRAIN assumed results were immediately available. COMPUTE fills this gap.

4. **Dependency tracking requires fed_tiles_ set** - We need to know when tiles
   have been fed to compute to satisfy COMPUTE dependencies.

## 8. Performance Impact

| Metric | Before | After |
|--------|--------|-------|
| Total cycles (64x64x64) | 941 | 1801 |
| DMA utilization | 8.7% | 99.9% |
| BlockMover util | 95.7% | 45.0% |
| Streamer util | 60.3% | 31.8% |

The increased cycle count is expected because:
1. DMA now correctly serializes transfers (was incorrectly parallel before)
2. DRAIN waits for compute latency (32 cycles per tile)

The utilization changes reflect correct timing - DMA is now the bottleneck as expected
for a bandwidth-limited system.
