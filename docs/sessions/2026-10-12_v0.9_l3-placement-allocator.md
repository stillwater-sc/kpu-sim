# v0.9 L3 Placement, Step 2: the L3 Address and the Walker's Allocator

**Date:** 2026-10-12
**Version:** v0.9
**Status:** Complete (step 2 of 7, `docs/plans/l3-placement-at-lb.md`)
**Tests:** 272/272 (new: `test_csp_place`, 5 cases)

## 1. Summary

Every residency now has an L3 address, allocated once by the walker as it opens the residency and
freed when it is released. Every action that touches the residency carries the address. No level
executes it yet: L-B does that in step 3.

- `csp_program.hpp`:
  - `L3Address{l3_tile, slot, bank}`;
  - `Action::place` and `Residency::place`, plus `Residency::pinned` (the program named the slot);
  - `CspProgram::l3_banks` and `CspProgram::place`;
  - the disassembly prints `@l3[0]:slot/bbank`.
- New `csp/lang/place.hpp`: `L3Allocator` with the `fifo`, `lowest` and `bank-spread` policies,
  plus `take_at` for a slot the program names.
- The language (`parse.hpp`, `format.hpp`, `print.hpp`):
  - `machine flat(l3 = N, banks = B, place = P)`, where both options are optional;
  - `resident X @ slots(lo..hi)`, one slot per tile, in order.
  - Defaults are not printed, so every existing program keeps its canonical text and digest.
- `walk.hpp`: placement on every open (`resident`, `inherit`, and the writeback slot of `store` and
  `retain`). A Release returns the slot; a Retain keeps it live.
  - A named slot that holds a live tile is refused, naming the tile.
  - So are a slot count that does not match the tiles, and a slot outside the L3.

## 2. Decisions

- **The bank count is declared in the program, not read from the deployment.** The plan's Q4 says
  `bank = slot % l3.banks`, but the walker places with no deployment in hand: `compile` runs
  without a target, and `bank-spread` needs the count. So the machine clause gains `banks = B`
  (default 1), beside `l3 = N`, which is also a machine fact the program states.
  - Step 3 and step 6 will check the program's banks against the deployment's, as `l3` is
    already checked against `capacity_tiles` (`csp_level_supported`).
  - **This deviates from the plan's wording, and the PR raises it for review.**
- **Placement is looked up by residency.** `emit` fills `Action::place` from a map of the open
  residencies, so every call site that names a residency carries its address without threading a
  parameter through each one. The map holds only open residencies, so it is bounded by the L3's
  capacity.
- **`print` reproduces placement.**
  - It writes the policy and the banks in the machine clause, and `@ slots(s..s+1)` for each
    residency the program placed itself.
  - Every other slot is chosen again by the same policy, on the same sequence of opens and
    releases, so `compile(print(p))` has `p`'s slots (tested).
- **Validation stays symbolic.** The validator does not see slots. A collision between named slots
  is found when the walker places them: `compile`, or the first run that walks that far.

## 3. Wrong decisions

- **A dangling-iterator bug in my own test.** I built a vector from the `begin()` of one temporary
  and the `begin() + n` of another. Catch2 printed garbage. I fixed it by binding the vector
  first; no product code was affected.
- **My "is a build running" check matched itself.** `pgrep -f "cmake --build"` found the shell
  running that very command, so no build started. I now check with `ps -eo comm | grep -x ninja`.
