# v0.9 Delete the C++ L0 Derivations; `tile_characterize` Takes Its L0 from kpu-csp-gen (retire-l0-derivations PR 3)

**Date:** 2026-10-11
**Version:** v0.9
**Status:** Complete (PR 3 of 3; PR 4 is proposed and awaits review, plan Q4)
**Tests:** 271/271

## 1. Summary

#359 (PR 2) was merged. PR 3 removes the last C++ source of an L0:
- `include/sw/kpu/program/derive/` is deleted;
- `program_spec.hpp` loses `ProgramSpec`, `known_algo`, `derive`, `fill` and `result_operand`;
- `examples/characterize` takes each cell's L0 from kpu-csp-gen, as the trace L-B records.

The plan's deletion check (`git grep` for the derivation entry points outside `docs/`) now finds
only the history lines in `CLAUDE.md`, the corpus README and `trace_fixtures.hpp`'s "WRONG"
example.

## 2. Decisions

- **Each cell's L0 is kpu-csp-gen's program for the cell's L3** (plan §3.7). The L3 is the
  deployment's (`--l3-tiles`, or the `--deploy` spec's), as kpu-csp-gen's `--target` takes it. An
  unbounded L3 (0, the default) gets the L3 the schedule needs (`slots_needed`). The vector units
  come from the deployment too (`lang::target_from`).
- **A schedule that does not fit the L3 skips the cell, with the reason.** The derivation wrote
  an L0 for no particular L3, and the analytical model then reported it "infeasible". A trace is
  written for a machine, so generating one for a larger L3 than the cell has would characterize a
  program the machine cannot run. kpu-csp-gen refuses it, and the harness prints the refusal
  ("needs 17 L3 slots ... the L3 holds 8"). Recipe (d) in the README now says this.
- **Validation is a per-tile check against L-B** (§3.8): the trace runs on the platform at L-B and
  every operand is checked with `check_tiles`. A tile out of bound is printed, and the run exits 1.
  It used to print `err` and exit 0 whatever it was.
- **An unknown `--algo` is refused** (exit 2). It used to run matmul silently.
- **`program_spec.hpp` includes `stream_signature.hpp` directly** (§3.5); the stream map types
  came in through `stream/derive/matmul_streams.hpp` before. The fill's rationale (exact values,
  the `-march=native` FMA contraction, the LU `* 0.1f` incident) moved from `fill` to
  `fill_operand`, which survives.
- **Docs:** ADR 0004 §4.4 gains a status note (the bridge and the derivations are retired, and
  ADR 0001 D5's "L0 reference" now replays L-B's trace). `CLAUDE.md`'s Authorities paragraph says
  no C++ code writes an L0. The corpus README's history line records the deletion.
  `generate.hpp`'s LU comment no longer cites `derive_lu_tile_program`.

- **Review (CodeRabbit on #360).**
  - A zero `--sizes` or `--tiles` went to kpu-csp-gen, whose refusal the harness caught as "does
    not fit the L3". The cell was skipped and the run exited 0. Zero is now refused up front
    (exit 2; test `tile_characterize_rejects_zero_tile`). The L3 fit is now checked explicitly
    (`slots_needed` against the L3), so any other kpu-csp-gen refusal is an error.
  - ADR 0004's note now says the replay reproduces L-B's values bit for bit on every operand,
    rather than "matches the trace".

## 3. The characterization, before and after

The sweep diffed (`--algo matmul --sizes 64,128 --tiles 16,32 --compute-tiles 1,4 --dataflow os,hex`
and `--algo lu --sizes 32,64 --tiles 8,16 --compute-tiles 1,4`):

- **matmul:** identical, every column. The `TileDag` list scheduler orders by dependency, so
  kpu-csp-gen's panel order gives the same makespan, utilization and energy as the derivation's.
- **LU:** identical metrics. Only `err` moved, from about 1e-6 to 0. It was a reconstruction
  residual (|L·U − P·A| on a hand-made matrix); it is now the distance from L-B's values, and the
  platform's L-B run of the trace reproduces them exactly.

What is lost: the LU reconstruction residual was a check against mathematics, not against L-B.
By the user's decision (plan Q2), L-B is the one oracle and no test-only operator reference
exists, so it is not kept. `test_tile_program` still checks the LU kernels by P·A = L·U reconstruction on L-B traces.
