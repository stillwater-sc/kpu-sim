# v0.9 `kpu-csp-gen`: The CSP Program Generator (kpu-run-csp-programs Step 1)

**Date:** 2026-10-10
**Version:** v0.9
**Status:** Complete (step 1); step 2 (`kpu-run --program file.csp` at L-B and L-CA) next
**Tests:** test_csp_gen 6/6 (new), 5 CLI tests (new); the CSP language, linear and driver suites
unchanged and passing; full suite in the PR

## 1. Summary

The architect asked for a plan for `kpu-run --level cycle-accurate`. My first draft ran L-CA from
L0, lowered with Belady residency. The architect rejected it: **L0 is a trace format**, and it
should not drive functionality.

The plan was rewritten (`docs/plans/kpu-run-csp-programs.md`):
- `kpu-run` is the simulator. It takes a CSP program, which configures its data path, and
  executes the operator at every level, L-T1 included.
- Producing programs is a separate executable.

Step 1 builds that executable, `kpu-csp-gen`.

## 2. Decisions

- **Generate text, not an AST.** The schedules are written as structured program text and then
  validated. The language's printer prints the flat IR, which loses the loops, so it cannot be
  the generator's output path. The text is what a person would write, and what `kpu-run` will
  read.
- **One canonical schedule per operator (Q4).**
  - matmul: output-stationary panels, `--orient col|row`, 2nt + 1 slots;
  - linear: + the bias tile, `--place`, 2nt + 2 slots;
  - LU: A resident whole, nt^2 slots.

  A schedule that does not fit is refused with its slot count; it is not quietly degraded to a
  different schedule. A schedule search belongs to this tool later, not to the simulator.
- **LU in the derivation's op order,** so the program's trace is bit-identical to
  `derive_lu_tile_program`. That makes the derivation a second, independent oracle in the tests.
- **The unfused linear epilogue is a separate pass over C.** It does not depend on the
  orientation, and it states the second DRAM round trip plainly.
- **The machine's L3 is an input** (`--l3` or `--target`). Orientation and placement are
  options: the schedule-vs-machine rule.

## 3. Found on the way

**The trace's L0 left out a fused epilogue.** A tile context's stages ride the Drain and
Writeback actions, so its bias and activation never appeared as L0 ops. The trace's L0, run by
`TileProgramReference`, computed `A . B`. Step 2 uses that L0 as the value oracle, so every fused
program would have been compared against the wrong answer.

The new test caught it by comparing the trace's own reference against the derivation's. The
walker now records each stage as an L0 op at the point it applies. The existing suites are
unchanged, because nothing compared against the trace's L0 for a fused program until now.

## 4. Verification

- **`test_csp_gen` (297 assertions).** Every generated program, at its smallest accepted L3:
  - validates, with the claimed peak;
  - compiles, with the same peak and loads;
  - runs at L-B from the trace and from the stream;
  - equals the L0 derivation's reference bit for bit, as does its own trace's reference.

  Covered: matmul at 64/16, 128/32 and 80/32 (trailing tiles) in both orientations; linear at
  96/32, all 32 combinations of placement, activation and orientation; LU at 64/16, 96/32 and
  48/16.
- **Refusals:**
  - one slot short (17 vs 16; 18 for fused linear; LU 15 for 4 x 4);
  - placement against a target (atan at bm.egress and at the fabric);
  - bad algo, orient, place, or a missing L3.
- **CLI:**
  - matmul written;
  - LU from `kpu_s1.json`;
  - refused for L3 (exit 1, nothing written);
  - refused for placement (S1 declares no vector units);
  - a bad option (exit 2).

## 5. Wrong Decisions

- **The first `kpu-run` plan drove L-CA from L0.** It took the existing plumbing's shortest path
  and contradicted ADR 0004 §4, decided the day before. Lesson: when a decision has just
  reclassified an artifact, check every new plan against it before writing it, especially when
  the plumbing still assumes the old role.
