## 1. Summary

`kpu-run --program file.csp` gains `--step`, `--step-limit` and `--timeline`, which until now
existed only on the L0 path:
- `--step` walks the program at L-B (one action per step, applied) or at L-T1 (the run's records,
  replayed in start order);
- `--timeline` writes the L-T1 run as Chrome-trace events, one per leg.

Both go through the platform: `VirtualPlatform::step_begin` takes a `CspProgramHandle`. The L0
path's `--step` and `--timeline` are unchanged; they leave with the L0 L-T1 executor in 4e.

## 2. Decisions

- **A separate stepper interface (`CspStepper`), not a mode of the L0 `Stepper`.** The L0
  `StepEvent` names an op index, a `TileOpKind` and a `Hop`, all of which belong to the trace.
  A CSP step names an action, its kind, its tile and its tile context. Forcing one into the
  other would have meant a trace vocabulary in the program's stepper, and 4e deletes the L0
  one anyway. The platform's cursor shape (`executes()`, `run_result()`, `step()`) is kept,
  so a caller reads both cursors the same way.
- **L-T1 occupancy is a function of the cycle, not of the step count.** A step reports what is
  busy and held at its start cycle: every leg and slot that has begun by then and not ended
  (an end at `t` frees before `t`'s begins, as L-T1's peak counts it). Counting only the steps
  already taken would make two records at one cycle report different occupancy for the same
  instant.
- **Station occupancy is reported at both levels.** The L0 stepper's header says it cannot
  report it, because the L0 executor publishes only its peak. The program's L-T1 publishes
  its slots (step 4b), and L-B holds its channels, so both report it. `BehavioralInterpreter`
  gains `held(Chan)` for this.
- **A Release is a step but not a timeline event.** It is a record (zero length, no process),
  so stepping shows when the credit returned. But it is not an interval on any process, so the
  Chrome trace leaves it out. The slot it ends is the `.tflow` record's to draw.
- **`--step` picks the finest of L-B and L-T1 that ran,** as the L0 path picks the finest
  level. L-CA's step is a cycle (#283), so a run with only L-CA is refused, with that reason.

## 3. Observed

- On the linear corpus at L-T1, the first step at cycle 0 shows 36 of 128 slots held while 8
  DMA lanes are busy. A Load takes its slot when its data and credit are ready, not when a DMA
  lane frees, so later Loads in program order hold slots before their transfer starts. That is
  L-T1's model (step 3) and the `.tflow` record already shows it (4b). The how-to now says so,
  so a reader does not take it for a bug.

## 4. Wrong decisions

- None in the code. Stale background watcher loops from the previous session were still
  polling and were stopped. They had been left running after their results were read.
