**Date:** 2026-10-06

## 1. Summary

Started step 4 of `docs/plans/noc-port-arbitration.md`: the CSP NoC hub and port processes.
The step was split. 4a builds the fabric on its own; 4b wires it into
`ConcurrentTimingExecutor`. 4b needs a destination L3 tile per block, which the executor's
pooled L3 does not have, and the DMA burst window from DRAM step 3. Running the plan's own
liveness test showed that the design as written (greedy injection, four shared buffers per hub,
shortest-path routing) deadlocks a saturated T64, and that the documented bubble fallback did
not fix it. The architect chose dimension-ordered routing with per-input queues and the bubble
rule (Q7). That design is implemented, live on every pattern tried, and mutation-checked.

## 3. Technical Decisions

**Decision 1: Split step 4 into 4a (fabric) and 4b (wiring)**
- **Choice:** Build and test the processes standalone; wire them in later.
- **Alternatives Considered:** Invent an L3 placement rule now and wire everything in; do DRAM
  step 3 first.
- **Rationale:** The executor has one pooled L3, so a block has no destination hub. Inventing a
  placement policy without review is the wrong order. Asked and decided.
- **Files Modified:** new `include/sw/kpu/timing/noc_{topology,hub_process,port_process,fabric}.hpp`

**Decision 2: Liveness by DOR + per-input queues + entry queues + bubble (Q7)**
- **Choice:** The architect chose it from three options. The other two were landing the deadlock
  as a documented xfail, and raising the shared buffers to 8 on empirical evidence only.
- **Rationale:** It is the standard deadlock-free scheme for a torus. The measurements:
  - Greedy with a shared pool deadlocked at 4 and 6 buffers on every seed.
  - The injection-only bubble deadlocked later.
  - The bubble on injection and turns, over a shared pool, deadlocked sooner: its argument
    needs a queue per ring.
- **Consequences, stated in the plan:**
  - The spec minimum is now 8, a multiple of 4: an entering block needs two free slots.
  - Injected and L3-sourced blocks wait in entry queues outside the rings. A column-port
    injection held in a column ring queue and then needing its row leg would break the order.
  - Q4's "shortest" now means shortest dimension-ordered.
- **Files Modified:** the timing headers, `deployment_spec.hpp`, the T4 and T64 fixtures,
  `test_noc_spec.cpp`, and the plan (§1.2, §3.1, §3.3, §3.5, §4, §5, §6, §7).

**Decision 3: The watchdog watches ring queues only (TF-HUB-2); entry wait is measured (TF-HUB-3)**
- **Rationale:** The bubble guarantees ring progress, not fair admission. At four slots per input
  under same-ring traffic, an entry block waited past the 800-cycle bound while every ring kept
  moving. Firing on that would report starvation as deadlock.

**Decision 4: Completions happen at the end of tick(), for the next cycle**
- **Rationale:** Callers push between ticks. If a cycle's completions run inside the next tick,
  a push sees the cycle before its arrivals and releases. A BlockMover then loses a cycle per
  block, and a stream leaves gaps that an injection uses. With completions at the end of
  `tick()`, every push sees the fully completed start of its cycle.

**Decision 5: The §3.4 rate condition is read per engine**
- **Rationale:** An output queue belongs to one engine, and the whole ejection stream can be
  bound for it. The derived depth is sufficient exactly when that engine retires a block per
  block time. With that reading, an unattributed stall is impossible by the derivation, and the
  tests hold it at zero.

## 4. Issues Encountered

- **The plan's liveness test deadlocked** (Decision 2). Root cause: cyclic buffer dependency
  across row and column loops, through shared hub pools and non-dimension-ordered routes.
- **The TF-PORT-3 stream had gaps.** The first cause was the late-completion order
  (Decision 4). The second is that under the bubble, a single L3 -> L3 source enters at only one
  block per two block times. The test now drives an ejection stream, which is ring-phase traffic
  on the same fold channel at full bus rate.
- **A zero-latency DMA write held its output slot one extra cycle,** because writes retired
  before new ones issued. The order is now issue, then retire.
- `test_python_cpp_integration` cannot link here: `/usr/lib/x86_64-linux-gnu/libpython3.12.so`
  is missing. This is an environment problem, unrelated to this change.

## 5. Wrong Decisions

- **The first hub model pooled buffers across inputs** ("at least four blocks" read as a shared
  pool). The plan's §1.2 said "one per input", which is per-input queues. The pooled reading is
  what let the deadlock form across loops. Correction: per-input queues (Q7). Lesson: when a
  plan sizes a buffer "per X", model it per X before testing liveness.
- **The first TF-PORT-3 test assumed a lone L3 -> L3 stream saturates a fold channel.** Under
  the bubble it cannot. Lesson: derive the traffic rate a test relies on from the flow-control
  rule before writing the assertion.

### Addendum: the T16

T4 is a degenerate torus. Its row and column loops are the same two-hub ring, so every channel
is a fold link and no block ever passes through a port. The architect asked for a T16, a 4x4
board with proper four-hub rings in both dimensions. It adds:
- a layout and floorplan test, and `kpu_floorplan_t16` with its import round trip;
- NoC topology coverage;
- a ring-through ring-first test, which the T4 cannot express;
- a mixed-traffic liveness test.

Finding: saturated injection alone never passes through a T16 port. A port injects into its
nearer fold hub, and on a four-hub ring no shortest route from there crosses a fold link. L3 -> L3
moves do pass through ports, so the liveness test mixes them in.
