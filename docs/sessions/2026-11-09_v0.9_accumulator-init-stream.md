## 1. Summary

An accumulator can now start from something other than zero:

```
acc C[i, j] in fabric init D[i, j] { ... }   // C = A.B + D
acc C[i, j] in fabric init b[j] { ... }      // C = A.B + b, b broadcast down the rows
acc C[i, j] in fabric init C[i, j] { ... }   // C += A.B
```

The init is **one more edge stream**: the init tile is Moved (L3 → L2) and Fed (L2 → L1) into the
fabric before the accumulator's first call, and its values become the accumulator's. No init is
a clear, as before. This mirrors the RTL's bias, accumulate and `CLEAR` (esg #17 and #47) without a
write path into the accumulators.

## 3. Technical Decisions

- **Decision 1: the init is an edge stream, not a write into the accumulator** (the user,
  2026-11-09). The RTL loads its accumulator SRAM through the BlockMover. The user ruled that out
  for the array: it has only nearest-neighbour links, and a global path to every accumulator costs
  too much power and area. Everything enters from the edges, and an initial C value enters by a
  propagation recurrence like any other domain. ADR 0002 §3.3 (the fabric talks only to L1) stands
  unchanged. I had offered the alternative, the accumulator as its own memory written by the
  BlockMover; it was rejected.
- **Decision 2: syntax `acc ... init <tile>`** (the user's choice). The rejected alternative was a
  third operand on the first call, which would have meant splitting the k loop.
- **Decision 3: self-init takes over the residency.** `init C[i, j]` emits Move, Feed, then
  Release of C's residency, because the value lives in the fabric from then on. It also lets the
  accumulator and the residency share a tile key without the walker or L-B holding two copies.
- **Decision 4: the init's Feed carries `seeds`.** There is no new action kind. Every level reads
  the init from the Feed: L-B seeds the fabric, and L-T1 makes the first call wait for it.
- **Decision 5: L0 `ACC_INIT`, opset 1.4, recorded only with an init.** The trace stays a
  complete record of what is computed, so `TileProgramReference` remains the oracle. Programs
  without an init keep their opset, and the golden corpus is unchanged.
- **Decision 6: value order is init + Σₖ.** That is the RTL's order. In fp32 an init bias and an
  epilogue bias (`store ... via add(b)`) are therefore not bit-identical.
- **Decision 7: L-CA refuses an init** until its Streamer feeds a third stream (plan step 2).

## 4. Issues Encountered

  `tile_dependencies.hpp` was given the op's reads and writes too.

- Pre-existing and not from this change: gcc 15 `-Warray-bounds` in `tests/program/test_virtual_platform.cpp:515`
  (a false positive on `other.back()`), and gcc 15's `-Wmaybe-uninitialized` in
  `src/software/compiler/schedule_generator.cpp:484`. The local `build/` has `KPU_WERROR=OFF`; CI's
  gcc did not warn on main.

## 5. Wrong Decisions

- **I first proposed that kpu-sim model the accumulator as its own memory**, written directly by
  the BlockMover as the RTL's accumulator LOAD is. That would have amended ADR 0002 and added a
  global path into the array that the hardware must not have. The user corrected this: values
  enter the fabric only from its edges, by propagation. **Lesson:** when the RTL appears to
  write into the array directly, raise it as a question about the RTL, and don't mirror it. This
  is now in memory.
