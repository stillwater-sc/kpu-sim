# v0.9 L-CA From the Structured CSP Program: Step 1c.2 (Release Action, Windowed Driver)

**Date:** 2026-10-09
**Version:** v0.9
**Status:** Complete (1c.2); CSP-language step 2 (the linear operator) next
**Tests:** test_csp_driver 9/9 (3 new cases); full suite in the PR

## 1. Summary

Step 1c.1 made the structured program stream. L-CA could not yet run from that stream, because
`CspDriver` seeded each L3 entry with its residency's consumer count at the Load
(`TileDescriptor::l3_consumers`), and that count needs lookahead.

This step removes the lookahead.
- The executor takes the program's Release as an action.
- The driver pulls actions from the stream as the executor's backlog allows.

Running in a window exposed two places where the executor assumed the whole program was
scheduled up front. One of them computed wrong values.

## 2. Decisions

- **Release is the BlockMover's action.** The L3 entry's consumers are the Moves out of L3, and
  the BlockMover issues them, so the BlockMover retires the entry once the tile's Moves issued
  before the Release have completed.
  - Per-tile epochs (`l3_epoch`) order a tile's Moves and Releases both ways. A Move issued after
    a Release waits for that Release, so it moves the next residency's copy, never the old one,
    even while the old copy sits in L3.
  - Releases take zero time, like dedup moves.
  - A result's residency (opened by a Writeback) is still retired by its Store's ejection: the
    driver issues `schedule_release` only for residencies a Load opened.
- **`l3_consumers` is replaced by a flag, `l3_held`,** not kept beside it. It had no other user,
  and two retirement mechanisms for one entry would be one too many.
- **The window bounds the backlog** (`ConcurrentTimingExecutor::backlog()` plus the driver's
  pending Loads), not per-process queues. Every action's inputs precede it in program order, and
  every Release that frees a later Load's credit precedes that Load. So a prefix of the program
  is always executable, and a global bound cannot deadlock where the whole program would not.
  Tested from window 1 upward.
- **The window is a schedule parameter, default 256.** It caps how far the DMA runs ahead of
  compute, so it acts as the program's prefetch depth. That makes it a run option, not a machine
  field (the schedule-vs-machine rule).
- **The early-DRAIN fix retracts; it does not delay.** When a later call on the same accumulation
  chain is scheduled, the early publication is invalidated, unless a DRAIN not yet started is
  waiting for it (an earlier chain's result). This keeps the trace path bit- and cycle-identical.
- **Fill accounting:** "last call of the chain" now also requires the tile's DRAIN to be
  scheduled. On the trace path that is always true, so cycles are unchanged. In a window too
  small to include the DRAIN when the last call starts, the drain half goes uncharged:
  under-charging by at most half a fill per chain, instead of over-charging every call.

## 3. Verification

- **Trace path:** the step-2 cycles are reproduced exactly: 43,968 (S1 256^3) and 38,089 (DMA
  window 32). The lowered programs at L3 4, 8 and 16 give 18,006, 14,462 and 9,890 cycles.
  Release-based retirement times exactly as the consumer counts did.
- **Stream** (written matmul, 128^3 / 32^3, S1):
  - The whole stream at once equals the trace: same cycles, actions, loads and values.
  - At windows 1, 2, 4, 16, 64 and 256: bit-identical to the reference, with 32 loads, and the
    driver holds at most window + 1 actions.
  - Cycles: 24,588 / 19,675 / 18,506 / 16,008 / 12,642 / 9,985. Window 256 equals the trace.
  - Inputs not shaped as the program declares are refused by name.
- **Release, directly on the executor:** one tile, two residencies. The Release follows both
  earlier moves. The move issued after it waits for the second load, even though the first copy
  is still in L3. L3 credits return to their initial count.

## 4. Wrong Decisions

- **My first stream test replaced the compiled trace's `source` with a derived L0 program,** to
  give it values. That swapped in a different op list, and the Calls' `l0_op` indices pointed at
  the wrong ops. Values are now copied operand by operand.
- **I first matched the BlockMover's events by a "BM" name prefix.** Movers are named
  `L3[..]:BM`. The test failed rather than passed vacuously, because it requires two Releases.
- **The executor bug was latent since step 2.** Its accumulate path asked whether a call was the
  last one *scheduled* on a tile, which only means "last" when everything is scheduled up front.
  Lesson: any rule that reads a scheduled count is a lookahead assumption. Windowed issue is the
  test that finds them.
