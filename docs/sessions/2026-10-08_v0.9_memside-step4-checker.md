# v0.9 Memory-Side Debugger Step 4: The Checker, and a Debuggers How-To

**Date:** 2026-10-08
**Version:** v0.9
**Status:** Complete (step 4); step 6 (characterization) remains
**Tests:** test_mflow_check.py 21/21; test_memory_side_harness 8/8; full suite in the PR

## 1. Summary

The architect asked for a how-to for working with the debuggers, then step 4.
- `docs/tools/debuggers-how-to.md` covers both record, check and view debuggers:
  - which one to use, and how to record, check, view and share;
  - the `kpu-memsim` scenario format and request models;
  - the panels and controls, and a table for reading the memory side;
  - the ctests.
- `tools/trace/mflow_check.py` checks TF10, TF11 and M1-M5. Its first run on the T4 bundle found
  a recording bug in DRAM step 1's bridge, which is now fixed.

## 2. Decisions

- **DRAM timing is checked on controller ticks, and the record carries them (version 2).** One
  T4 executor cycle is 4.27 ticks, and tRCD is 19. At cycle grain, either a check is loosened
  until it misses a violation of a few ticks, or it reports false violations from rounding.
  Adding four u64 tick columns per command makes every DRAM check exact. Bumping the version
  makes old bundles refuse by name, not fail mysteriously; they are a day old.
- **The timing table comes from the controller, not the spec.** `DramBridge::timing_table()`
  reports the scaled table the controller actually runs. M5 checks the model against what it
  claims to run, and the provenance stays in `timing_note`.
- **M5 is wider than the plan's list.** tRAS, tRC and tRFCpb were added. They are the
  controller's own `can_activate` and `can_precharge` constraints, and the run holds them.
- **The self-test tightens the table to test M5 per parameter.** Mutating the data to break each
  constraint needs a matching command pair per parameter, which is fragile. Raising a table
  entry tests the same code path for all ten parameters. One data mutation (a CAS one tick
  inside tRCD) shows the check reads the data.

## 3. Bugs Found

- **The bridge recorded later command points up to a cycle late.** It converted a command's
  end and data window from ticks as `issue cycle + ceil(dticks / tpc)`, which rounds twice.
  - M4 found 1,491 of 6,400 T4 bursts completing a cycle before their own data window ended.
  - Every one of 7,385 issue cycles equals `ceil((k + 1) / tpc)`, the executor cycle in which
    tick k runs. Every burst's completion equals that formula on its data-end tick.
  - Fixed: each point is converted with that formula, never before the issue cycle. The run
    is unchanged; only the record moved.
  - `test_memory_side_harness` now pins every command point and `burst.done == data_end`
    exactly.

## 4. Verification

- On the T4 run, `mflow_check.py` passes every check (TF10, TF11, M1-M5) over 6,400 bursts and
  7,385 commands. Before the fix it failed M4.
- `test_mflow_check.py` passes 21/21. Each invariant fails on its broken case, and an
  unreadable bundle exits 2.

## 5. Review (CodeRabbit, two findings, both fixed)

- **A malformed bundle could crash the checker.** A `dma`/`dmabuf` name with no `[index]`, or a
  non-numeric `burst_bytes`, raised inside `check()`, so the checker exited 1 ("violations")
  instead of 2 ("unreadable"). Both are now validated in `load()`; the self-test has a case for
  each (23 cases).
- **The viewer checked alignment before the dtype.** An unknown dtype failed with a generic
  TypeError instead of the named error. The order is fixed; `test_viewer.py` pins both messages.
