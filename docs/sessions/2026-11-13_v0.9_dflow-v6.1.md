## 1. Summary

`.dflow` version 6 described two things unlike the RTL:
- the RTL's STORE drains the accumulator straight to L3, but v6 allowed only acc → l2 and then
  l2 → l3;
- the RTL's L3 is flat memory addressed in words, with no slots and no credits, but v6 declared
  only a slotted L3, checked against the machine.

Version 6.1 adds both. Nothing kpu-sim writes changes: its L-B record stays a valid 6.0 record.

## 3. Technical Decisions

- **Decision 1: a minor version, not v7.** The spec says a change to the `layers` or
  `event_kinds` list needs a new version. 6.1 changes neither: it adds a layer pair to `DRAIN`
  and a second L3 form. So it is `"minor": 1` on version 6. A reader of 6.1 reads 6.0, and a 6.0
  record must not use 6.1's additions, so an old record cannot claim them by accident.
- **Decision 2: the store is a `DRAIN`, joined to the `WRITEBACK`.**
  - **Alternative:** a new event kind `STORE`, which would change `event_kinds` and so need v7.
  - **Rationale:** it drains the accumulator, so `DRAIN`, with its `DRAIN_ROW` children. Its
    destination is L3, which the `WRITEBACK` action names. It also stands for the tile's `DRAIN`
    step, so full joining still has one transaction per data step.
- **Decision 3: what an L3 credit is.** My first rule refused any credit to or from l3. It failed
  the sample's Feed credits, which go from l2 to l3 to free L2 rows. A credit frees its source, so
  the rule refuses a credit whose source is l3.
- **Decision 4: the steps keep their slots.** A word-addressed record's steps are still the CSP
  program's actions at its slots; the host maps slots to words. E5 checks instead that a residency
  keeps one word address.

## 4. Issues Encountered

- The first L3-credit rule was too broad (Decision 3). The sample caught it.
