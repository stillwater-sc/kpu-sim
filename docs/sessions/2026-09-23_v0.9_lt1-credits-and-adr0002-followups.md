## 3. Technical Decisions

### Decision 1: New L3 slots are acquired in program order

- **Choice:** An op may take *new* slots only when no earlier unfired op still needs any.
  An op whose tiles are all resident fires freely.
- **Alternatives considered:** (a) capacity-only admission; (b) the weaker rule "don't
  promote a later ready op past an earlier waiting one".
- **Rationale:** Both alternatives deadlock. Feeds are dependency-ready immediately and
  take every slot, while the computes that would retire those tiles are waiting on those
  very feeds — classic hold-and-wait that **no ordering among *ready* ops can break**.
  Ordering *slot acquisition* bounds the live set by the program-order live set, making
  any budget at or above `peak_live_tiles` sufficient.
- **Measured** (64³ T=16 GEMM; 48 distinct tiles; live set 21; greedy peak 29):

  | `l3_tiles` | weaker rule | shipped rule |
  |---|---|---|
  | unbounded | 1184, peak 29 | 1184, peak 29 |
  | 29 and above | 1184 | 1216 |
  | 25 | **wedged** | 1216 |
  | 21 | **wedged** | 1312 |
  | 20 | — | refused |

  The weaker rule is not universally broken: it matches unbounded at ≥29. What it cannot
  do is run between the true live set (21) and its own greedy peak (29) — exactly the
  range this tier exists to model.
- **Files:** `include/sw/kpu/program/tile_transaction_executor.hpp`

### Decision 2: Credits are returned when a tile's last user completes

- **Choice:** A per-tile unfinished-user refcount, decremented at completion.
- **Alternatives considered:** release at the highest-*indexed* user, computed statically
  (what shipped first).
- **Rationale:** `TileDependencies` orders writer→reader and deliberately leaves
  reader→reader unordered, so concurrent readers exist and the higher-indexed one can
  finish first. Releasing on it frees a slot an earlier reader still holds, undercounting
  residency and letting a run **exceed the capacity being enforced**. Design note §5
  already said "released when the last consumer completes"; the static index was an
  approximation of a sentence already written down.
- **Files:** `tile_transaction_executor.hpp`, `tests/program/test_tile_transaction_executor.cpp`

### Decision 3: Windowed scan in the hot path, exhaustive only before throwing

- **Choice:** Scan up to 32 queued entries per firing decision; scan exhaustively **only**
  as a precondition of raising the wedge diagnosis.
- **Alternatives considered:** (a) window only; (b) always exhaustive (the reviewer's
  suggestion).
- **Rationale:** Both are unacceptable, and the second was measured rather than argued.
  Window-only can throw a **false refusal** when the op that would release a slot sits
  past the window — demonstrated, not hypothesised (40 feeds at a 5-tile budget). Always
  exhaustive walks the whole backlog on every completion: a 512³ T=16 GEMM (99,328 ops)
  went **559 ms → 290,473 ms**, quadratic. Paying for the full scan only where the
  alternative is throwing makes false refusals impossible at ~zero common-path cost.
- **Files:** `tile_transaction_executor.hpp`

### Decision 4: Firing passes repeat while a pass makes progress

- **Choice:** Repeat whole passes while any pass fires an op; count a credit stall only on
  a pass that fires nothing anywhere.
- **Rationale:** Movement queues are scanned before compute, so a compute firing can hand
  the seeker to a movement op whose queue the pass already walked past — idling a lane and
  booking a stall against capacity that was available. Amortised, not quadratic: a pass
  repeats only when it fired. **The schedule got strictly better** (512³ tight makespan
  540,720 → 540,704, matching what a full rescan finds) at ~2× on the tight path.
- **Files:** `tile_transaction_executor.hpp`

### Decision 5: #254 closed as superseded, not fixed

- **Choice:** `not_planned`, with a per-DoD mapping and an explicit statement of what
  remains.
- **Rationale:** Three of four DoD items are delivered by #264's *new* executor; the
  fourth (calibration band) is increment 6. But the path #254 cites is **not repaired** —
  verified: `ResourceTimeline::schedule_compute` at
  `src/software/isa/transactional_program_executor.cpp:57` is still defined and still
  never called, while `src/models/transactional/memory_controller.cpp` no longer exists.
  Repairing it would duplicate the tier that now exists, so its removal was pointed at
  #266 rather than claimed as done.

### Decision 6: ADR 0002 follow-ups filed with enforceable definitions of done

- **Choice:** #281 (CSP derivation), #282 (`VirtualPlatform`), #283 (L-T2 interpreter),
  #284 (backdoor interface), #285 (`kpu-run`), #286 (visualization).
- **Rationale:** The invariants are written as things a test can enforce, not prose — e.g.
  #284 requires a backdoor transaction to be **inexpressible** in the program IR, and #283
  requires "no transaction reads a compute tile on the data path" to be asserted
  structurally. #286 is grounded in the existing `sw/trace/resource_tracker.hpp` +
  `trace_exporter.hpp` + `tools/visualization/` stack rather than proposing a fifth path.

## 4. Issues Encountered

| Symptom | Root cause | Fix |
|---|---|---|
| Every finite capacity below 29 deadlocked | Hold-and-wait: feeds take all slots; their consumers aren't ready yet | Program-order slot acquisition (Decision 1) |
| A run could exceed its own L3 budget while reporting a healthy peak | Release at highest-indexed user, not last completion | Refcount (Decision 2) |
| Free lanes idled with capacity available; stalls over-counted | Seeker computed once per `try_fire`; queues scanned once | Refresh the seeker; repeat passes (Decision 4) |
| Feasible program refused as a wedge | Scan window hid the op that would release a slot | Exhaustive pass before throwing (Decision 3) |
| Watcher declared a PR clean without a review of that head | `gh pr checks` aggregates statuses that may belong to an older commit | Gate on the CodeRabbit **commit status for the head SHA**, timestamped after the head commit |

## 5. Wrong Decisions (CRITICAL)

**Eight, and the honest count matters more than the flattering one.**

1. **Shipped increment 4 with the static-index release bug.** Design note §5 already
   specified release-on-last-completion; I implemented a cheaper approximation of a
   sentence I had written myself. *Lesson: when the spec states a rule, implement the
   rule, not something that agrees with it on the cases I happened to imagine.*

2. **Shipped two scheduling fixes with no tests** (rounds 2 and 3), which is precisely why
   there was a round 3. *Lesson: a fix to scheduling logic without a test that fails
   before it is not a fix, it is a hypothesis.*

3. **Proposed a scan window that was unsound**, trading a correctness hole for a
   performance bound, in a repo whose CLAUDE.md ends with "correct code is more valuable
   than fast code". *Lesson: when I catch myself bounding a scan for speed, check first
   whether the unscanned case can be wrong, not just slow.*

4. **Claimed the weaker rule "wedged at EVERY finite capacity."** Too broad: it matches
   unbounded at ≥29. Worse, I had copied the claim into three files, so one wrong sentence
   needed three corrections — twice. *Lesson: a measured number should live in one place
   with the others pointing at it.*

5. **Claimed "below 29" after writing that `l3_tiles == 0` means unbounded** — the
   quantifier included the one value that provably never wedges. *Lesson: when a field
   carries a sentinel, state the sentinel wherever the field is quantified over.*

6. **Claimed any budget below `peak_live_tiles` refuses.** It is sufficient, not
   necessary; the shared-reader program has a static peak of 6 and completes in 5. Found
   by my own probe, which is the only reason it is not still in the docs.

7. **Told the user a merged commit was unreviewed.** `064a5bc` had been processed — a
   clean incremental review posts a commit status and *no* review object, so my
   "review object must exist" check reported "unreviewed" on exactly the runs that are
   clean. I asserted a gate failure that was my gate's failure. *Lesson: verify the
   signal's semantics before reporting its absence as a fact.*

8. **Two process slips in one turn:** launched a watcher with `nohup &` (no notification —
   the exact failure the memory rule exists to prevent), then killed my own shell with
   `pkill -f watch279.sh` because the pattern matched the command line running it.

**Omission:** increment 4 merged without a CHANGELOG entry, though increments 2 and 3 both
have one. Caught while merging and fixed in #280.

**Not skipped:** no test was skipped, disabled or marked for later at any point. Every
review finding was either fixed or answered with evidence — one was answered and *partly*
declined (the unbounded-scan suggestion), with the 290-second measurement as the reason and
the correctness half of it implemented.
