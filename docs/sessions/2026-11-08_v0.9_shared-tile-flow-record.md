# v0.9 The Shared Tile-Flow Record: `.dflow` Version 6 (#386)

**Date:** 2026-11-08
**Version:** v0.9
**Status:** Complete (spec, checker, reference writer, RTL sample, L-B writer, viewer)
**Tests:** gcc, the full suite: 308/308. clang: `ctest -L domainflow` 31/31, and `test_domain_flow_record` (18 test cases).

## 1. Summary

kpu-sim and the KPU RTL now share one record format: `.dflow` version 6, specified in
`docs/plans/shared-tile-flow-record.md`. It adds, over version 5:
- the level and the producer;
- time, only at a timed level: a cycle column on the events;
- each layer's geometry, with layers that aren't modelled declared so;
- an `events` table (transactions, credits, tokens, row progress) whose identities both sides share;
- per-operand element types (int8, int32, fp16, bf16, fp32, fp8) in a byte payload;
- operand domains (dense, lower, upper, band, a padding window);
- expected values beside the actual ones;
- a result block (cycles to result, the values' verdict), which CI gates on.

kpu-sim's L-B writer emits version 6. `dflow_check.py` checks it: G1, T1, E1-E5, X1-X3, and `--result`.
`dflow_writer.py` is a standard-library writer for kpugen and systars to vendor.
`dflow_rtl_sample.py` writes a hand-written RTL-level sample. Its schedule is identical, table for
table, to L-B's run of the same program. The domain-flow viewer opens version-6 records.

## 3. Technical Decisions

- **Decision 1: version 6, not 3.** The issue says "extend `.dflow` to version 3", but versions 3 to 5
  had already shipped (the L-T1 overlay, the fabric, L2 staging). The additions are version 6.
- **Decision 2: kpu-sim's writer moves to v6 in this PR** (the user's choice, 2026-11-08). The
  alternative, keeping the writer at v5, would have left two formats in flight.
- **Decision 3: one byte payload for values** (the user's choice). `elements` is a `u8` column,
  `snapshot.first` is a byte offset, and an element is decoded by its operand's type. The C++ record
  keeps fp32 elements and element offsets in memory, which keeps the API unchanged. Rejected: f32 plus
  a typed table per width, which means two decode paths forever.
- **Decision 4: identity is attributes, not ids.** The key is (kind, process, tile, layers and
  addresses, loop indices, row, beat). `id` is local to a record, and `lane` is excluded, because
  engine counts differ between kpu-sim and the RTL.
- **Decision 5: enums are part of the format.** `layers` and `event_kinds` are written verbatim, and
  a reader refuses any other list.
- **Decision 6: out-of-domain elements are stored as zero bytes** (X2), so digests and comparisons
  are deterministic. The viewer draws them as a checker, never as a zero value.
- **Decision 7: the D3 gate is `--result`.** It prints the cycles and a SHA-256 of each operand's
  finals. It reads no event column, and a test pins that.

## 4. Issues Encountered

- **`build/` was stale, and gcc 15 `-Werror=maybe-uninitialized` fired in
  `src/software/compiler/schedule_generator.cpp:484`.** The code is unrelated and the warning
  predates this branch. I rebuilt `build/` locally with `KPU_WERROR=OFF`; the code is not changed.
- **Node.js is not on PATH** (it is in `~/.nvm`). `test_viewer.py` silently skipped its data-layer
  tests until I put Node on PATH. The new decode-parity test and the RTL-sample comparison were
  therefore verified with Node present.
- **The viewer's layout test failed** at first: the inspector showed extra rows only for tiles with a
  domain mask. Fixed: on a v6 record the inspector always shows both rows.
- **A JSON round trip** turned a large float (`58828270132527100`) into a Python int, which the
  decode-parity test then compared unequal. Fixed: the test compares as floats.

## 5. Wrong Decisions

No wrong decisions identified this session. One spec sentence first claimed that a test pinned more
D3 invariance than it did ("splitting a transaction or adding a credit"). I corrected it before
committing to what the test actually checks: renumbering every row event's beat.
