# v0.10 The Combiner's Integer Epilogue and the Fused-Operation Matrix (#427)

**Date:** 2026-11-16
**Version:** v0.10
**Status:** in review (draft PR). #427 stays open: a per-channel scale, the MX format's stored
bytes, an init through the Combiner, the weight-stationary array timing, and the RTL contracts
(part 3) remain.
**Tests:** see §6.

## 1. Summary

A requantized result's context was its scale and nothing else, so an int8 linear (bias,
requantize, relu) could not be written. #427's L-B item, "bias, activation, scaling", held only
for fp32 results. This PR adds the integer epilogue:
- a bias before the scale, in the accumulator's type;
- relu after the scale, on the integer result.

Every level computes it. #427's fused-operation matrix (bias x scale x activation x format, on
OS, WS and IS) is now tested in both halves, the integer and the real.

The work also found a defect already on main: a deployment file could not list `scale`,
`mxint8` or `mxfp8` among a vector unit's operations. `kpu-run` therefore could not run a
requantized or block-format program from a file; only in-memory specs, which every test used,
could.

## 3. Technical Decisions

- **Decision 1: each stage computes in the type the values have where it runs.**
  - A bias comes before the scale, so it adds to int32 accumulator values, and the vector is
    declared int32.
  - relu comes after the scale, on int8.
  - The order is the Combiner's (bias, scale, activation, format), which
    `resolve_result_context` already enforces.
  - Alternative: a bias in int8, added after the scale. That is not how a quantized layer's bias
    works: it is in the accumulator's scale.
- **Decision 2: the bias wraps, as the MAC does.** The gemm's int32 sum wraps modulo 2^32 (a
  32-bit register), so the bias added to it does too. Saturating there would make the bias behave
  unlike the accumulator it joins. Saturation is the scale's job, into int8.
- **Decision 3: relu is the only integer activation.** gelu, silu and atan need real values.
  With the symmetric quantization the scale implements (zero point 0), relu on int8 is
  `max(0, x)`. A block format converts real values, so it is refused on an integer result.
- **Decision 4: opset 1.8.0, with no new field.** The trace records the bias and relu as the
  existing `BIAS_ADD` and `ACTIVATION` ops, on an operand whose `acc=` differs from its type. A
  1.7 reader parses them, and its kernels refuse them, since they compute in fp32 only. So
  MIN_CONSUMER stays where it is, as `opset_for`'s rule requires. A file writes 1.8.0 only when
  it holds one of these ops: a plain requantized matmul stays 1.7.0.
- **Decision 5: the words' type travels with the stage.** `bias_tile` and `activate_tile` take
  it, defaulting to fp32. L-B tracks it through the context: the accumulator's type until the
  scale, then the tensor's. L-CA's `VectorStage::word_type` carries it, set by the driver from
  the stage's position in the Combiner's order.
- **Decision 6: the deployment's vector operations are the language's.**
  `platform::kVectorOps` lists them, and a test checks it against `parse_veop` both ways. The
  platform layer does not include the CSP program header.

## 4. Issues Encountered

- **A deployment could not declare the Combiner these programs need.**
  - Found when the first `kpu-run` of a generated requantized linear was refused:
    "combiner.ops: 'scale' is not a vector operation".
  - The check predates the scale and the block formats; the tests built their machines in
    memory.
  - Fixed, with a fixture (`kpu_s1_combiner.json`) and a CLI test.
- **A test that never finished.** The fp32 matrix test rewrote the generated context with a
  find-and-replace loop. When the kept stages were all three, the replacement contained the text
  it replaced, so the loop matched its own output forever. Each cell, run alone through
  `kpu-run`, took under a second, which showed the bug was in the test. The loop now resumes
  after each replacement.

## 5. Wrong Decisions

- **`pkill -f` on a pattern my own command line contained.** I meant to stop the hung test. It
  killed the shell that ran it instead. This is the same mistake as the self-matching
  `pgrep -f` wait in the 2026-11-15 sweep session (`2026-11-15_v0.9_deploy-sweep.md`). Lesson,
  now in memory: stop a process by its task, or by an exact PID, never by a pattern that my own
  command contains.

## 6. Verification

```bash
build/tests/program/test_csp_requant
build/tests/program/test_csp_block_format "Combiner: the fused-operation matrix*"
build/tests/program/test_deployment_spec "a vector unit may list*"
(cd build && ctest -R linear_requant)
```

- **The integer matrix:** {bias, none} x {relu, none} with the scale, under OS, WS and IS.
  - Checked at L-B, L-T1 and L-CA, against a reference computed in the test: the int32 matmul,
    plus b[c] wrapped as int32, requantized, then max(0, q).
  - The test asserts that the data reaches the bias and produces negative values, so neither
    stage is a no-op.
- **The fp32 matrix:** every non-empty subset of {add(b[j]), relu, mxint8}, under OS, WS and IS.
  - Checked against the same linear with no stage, with the subset applied in the test, bit for
    bit at L-T1 and L-CA.
