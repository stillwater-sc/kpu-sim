## 1. Summary

Implemented the correct CSP architecture with proper separation of concerns between
DMA Engine (CSP Process) and Memory Controller (Communication Resource). The previous
implementation incorrectly replaced DMA Engine with Memory Controller. The correct
model keeps BOTH components working together where DMA submits requests to MC and
polls for completions, while MC handles DRAM contention (command bus serialization,
bank state machines).

## 3. Technical Decisions

### Decision 1: MC as IProcess with Submit/Poll Pattern

**Choice:** Keep MemoryController as IProcess that gets ticked by executor, with
DMA engines submitting requests and polling for completions.

**Alternatives Considered:**
- MC as pure internal resource (not an IProcess)
- Executor mediating all MC access

**Rationale:**
- Consistent with BlockMover and Streamer architecture
- Executor ticks all processes uniformly
- MC can emit its own timing events for tracing
- Clear separation: DMA = "what" (tile operations), MC = "how" (DRAM protocol)

**Files Modified:**
- `include/sw/kpu/timing/memory_controller_process.hpp`
- `include/sw/kpu/timing/dma_engine_process.hpp`
- `include/sw/kpu/timing/concurrent_timing_executor.hpp`

### Decision 2: Submitter ID for Multi-DMA Support

**Choice:** Add `submitter_id` field to requests/transfers so each DMA engine
only polls for its own completions.

**Alternatives Considered:**
- Each DMA has its own completion queue in MC
- Single completion queue with DMA matching by tile_id only

**Rationale:**
- When multiple DMAs share one MC, completions need to be routed correctly
- Without submitter_id, DMA0 could pop DMA1's completion and discard it
- Simple and efficient filtering mechanism

**Files Modified:**
- `include/sw/kpu/timing/memory_controller_process.hpp`
- `include/sw/kpu/timing/dma_engine_process.hpp`

### Decision 3: Tick Order (MC first, then DMA)

**Choice:** Executor ticks MCs before DMAs in each cycle.

**Rationale:**
- MC processes completions and makes them available
- DMA polls for completions, then submits new requests
- This ensures completions are visible in the same cycle they occur

**Files Modified:**
- `include/sw/kpu/timing/concurrent_timing_executor.hpp`

## 4. Issues Encountered

### Issue 1: Multi-DMA Completion Routing

**Symptom:** When multiple DMAs share one MC, completions were lost. Only 4 of 16
tiles loaded in multi-DMA test.

**Root Cause:** `get_completed_transfer()` returned any completion, but DMA
only processed those matching its pending requests. Non-matching completions
were discarded.

**Fix:** Added `submitter_id` to track which DMA submitted each request.
`get_completed_transfer(submitter_id)` only returns that DMA's completions.

### Issue 2: Drain Test Stalling Forever

**Symptom:** "Full round-trip" test reported 0 TILE_DRAINED events.

**Root Cause:** Streamer's drain operation waits for tile in `compute_result_tag_cam`,
but test never populated it (compute wasn't simulated).

**Fix:** Updated test to insert C tile into `compute_result_tag_cam` after
A tile is fed to compute, simulating compute completion.

## 9. Key Invariants

1. **DMA Engine defines the ISA** - `schedule_load/store` are the programming interface
2. **MC enforces DRAM contention** - 1 command/cycle, bank state tracking
3. **Multiple DMAs can share one MC** - Realistic for multi-channel configs
4. **Latency = DMA overhead + MC latency** - Composition of delays
5. **Submitter ID ensures correct completion routing** - Each DMA gets only its completions
