**Tests:** see §6.

## 1. Summary

#425's first item asks for the bubble view "at L-T1 first, then at L-CA". L-T1's report shipped
in #438. L-CA executes the program cycle by cycle, but it logs protocol events, not one record per
action, so the report could not read it. This PR matches L-CA's events back to the program's
actions, as records shaped like L-T1's. The same walk then explains both levels' bubbles, and
`kpu-run --bubbles` prints both.

## 3. Technical Decisions

- **Decision 1: L-CA's run as L-T1's records, not a second report.** The walk (a call's Feeds,
  a Feed's Move, a Move's Load, head-of-line holds, saturation) is the same question at both
  levels. A shared record shape means one explanation of a bubble, compared across levels.
- **Decision 2: match by kind, tile and program order.** A process takes one tile's actions of
  one kind in program order, so a transfer's START is the next unstarted action of its kind on
  its tile, and its COMPLETE closes the oldest one started.
  - A DRAM transfer is announced by both the engine and the memory controller. The second START
    finds the leg already taken.
  - Unmatched events are counted, not dropped silently. The count is 0 on every schedule tested.
- **Decision 3: ready means what it means at L-T1.** It is when the leg's inputs had finished, in
  the pairs the walk uses, and its credit was free.
  - Alternative: the cycle after the process's last stall on the tile. Rejected: a call logs no
    stall, and a queued action behind its process's head logs none either. With that rule every
    L-CA bubble came out as "in-order issue".
- **Decision 4: a one-cycle handoff is not a wait.** A process sees a completion on its next
  tick, so at L-CA a call starts the cycle after its last Feed completes. Without this slack each
  such cycle read as an issue hold and the walk followed the previous call back to the start.
- **Decision 5: the machine's lanes.** DMA engines, BlockMovers and compute tiles come from the
  executor's config. A Load's lane is the engine holding its request: the memory controller
  serves the transfer, so its events name the controller. Streamers' lanes are those the events
  name. Counting only the lanes a run used would make a lightly used process look saturated.

## 4. Issues Encountered

- **The first L-CA report blamed in-order issue for everything** (845 of 845 idle cycles). That
  led to Decisions 3 and 4. With them, the 48x48 matmul on S1 blames busy BlockMover lanes for
  812 of its 845 idle cycles, and its BlockMover is 88.7% busy. L-T1's report also points at the
  BlockMover.
- The BlockMovers' lanes came out as their component ids (100 and up). They are numbered from 0,
  as the streamers' are.

- **Review (CodeRabbit, PR #443): one finding and one trivial note, both valid.**
  - **A credit stall was read by every later action on its tile.** The stalls were kept by
    process and tile and filtered from each action's handover. A second Move on a tile then took
    an earlier Move's credit stalls as its own L2 wait, and its ready cycle with them. Now a stall
    belongs to the action its process had pending: stalls after the previous leg on that process
    and tile started are this leg's.
    - Test: a synthetic run of two Moves on one tile, the first stalled on 10..19. The second's
      L2 wait is 0, and its ready is the cycle after its Load. Without the fix the L2 wait is 90.
  - **A Store's DMA leg scanned every leg for its ejection** (O(Stores x legs)). It is a lookup by
    action now.

## 6. Verification

```bash
build/tools/kpu-run/kpu-run --program tests/program/corpus/matmul_48x48x48_t16.csp \
    --deploy tests/program/deploy/kpu_s1.json --bubbles
build/tests/program/test_csp_bubbles
```

- `test_csp_bubbles`, on OS, WS and IS:
  - L-CA's records are L-T1's actions, one leg each (a Store two), kind by kind;
  - every record has ready <= start <= finish <= makespan;
  - the reuse rows equal L-T1's, and L-CA's matched Loads are its DRAM loads;
  - the bubbles add up to the idle time, every cause is known, and no event goes unmatched.
- Checked by hand: WS and IS matmuls, an L2-staged OS matmul and a WS int8 linear. No event
  unmatched, and every cause known.
