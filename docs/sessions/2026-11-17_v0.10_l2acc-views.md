# v0.10 The Viewers Show the L2 Accumulator (#456)

**Date:** 2026-11-17
**Version:** v0.10
**Status:** in review (based on #455's branch, whose record columns it reads).

## 1. Summary

The domain-flow and tile-flow viewers read an L2 accumulator's partial as a staged copy, or not at
all. With #455's columns (`partial`, `merges`, `merge`) they now show the partials for what they
are. Found end to end on 2026-11-16 with a `kpu-csp-gen --dataflow ws --init bias` program.

## 2. Technical Decisions

- **Decision 1: the viewers read the record's columns; they do not infer.** Like the checkers
  (#455), a viewer that guessed a partial from step kinds would be inventing a rule. A record
  without the columns shows no partials, as it has none.
- **Decision 2: a partial is an accumulator chip in the domain-flow L2 box**, the same styling as
  the fabric's accumulators, labelled `p<slot> <merged>/<merges>` next to a staged copy's
  `s<slot> <fed>/<feeds>`. Its arrival is its overwrite Drain; an accumulate Drain merges into the
  same tile, so the state machine no longer resets it there.
- **Decision 3: the tile-flow swimlanes colour an L2 slot by what it holds in each bin** (a teal
  ramp for a partial), from the record rows at the bin's midpoint. The level-of-detail pyramid has
  occupancy only, so the kind comes from the record; one row per L2 copy keeps it cheap.
- **Decision 4: the test drives the pages as a person does.** The tile-flow page keeps its state in
  a closure, so the test reads the expected counts from the record (`tflow_check.load`) and finds a
  swimlane row by hovering until the tooltip names it, then clicks it.

## 3. Issues Encountered

- **"fabric chains NaN"** was a real bug, not a display slip. The tile-flow loader built each table
  as `{rows: count, ...columns}`, and the chain table has a column called `rows` (its PEs' rows),
  which replaced the count. So the header read NaN, and every loop `c < R.ch.rows` never ran:
  - the compute tiles' inspector said "no chains" on every run with a fabric;
  - the chain lookup under the cursor found nothing.

  The count is now set after the columns, and the column is read as `rows_col`.
- A second `NONE32` declaration in the domain-flow core stopped the whole page ("Identifier
  'NONE32' has already been declared"); the suites caught it (`l2acc_views`, and the viewer's own
  layout test, which could not load the page). Removed; the core already declares it.
- **Observed, not changed:** on this WS program, the tile-flow `cf[0]/out` row is red ("over
  capacity") for most of each chain. L-T1's results of consecutive chains overlap on the out row. That
  is a question about L-T1's output-stationary model of a WS program (#395), not about the viewer.

- **CodeRabbit's review (on-demand, 1.75 USD): three findings, all valid.**
  - The step panel did not show the merge's Combiner stages, or MERGE_INIT apart from a plain
    overwrite: #456's scope asked for both, and the record did not carry stages at all. The
    recorder now writes `steps.stages` (a bit per `csp::VeOp`) and `steps.init_tile` (optional
    columns, documented). The panel lists the stages in pipeline order and names the init on the
    first merge. Tests: the record test checks the first merge carries the init and its tile (D),
    and the later one none; the browser test checks MERGE_INIT and `init(D[..])` on the page.
  - The swimlane colouring scanned every L2 copy per bin, so a repaint cost
    slots × bins × copies. Each slot's partials are now a sorted interval list, searched by
    binary search.
  - It tested only each bin's midpoint, so a partial that ended before it painted the bin blue.
    The test is now an overlap over the whole bin.

- **The next review: two findings, both valid.**
  - Partials of different compute tiles can share a slot index and overlap (TF13 keeps them
    apart per compute tile), so the binary search's "disjoint, sorted by end" assumption could
    miss one. Each slot's intervals are now merged after sorting. The single-tile fixture cannot
    produce the case; the merge makes the search correct for it.
  - The domain-flow loader read `merges` only when present, so a record with `partial` and no
    `merges` threw. Each optional column now defaults to zero on its own, as the C++ reader
    does. Test: such a record loads and steps through a partial (it failed before).

## 4. Wrong Decisions

- **I left the stages out of the first push without saying so.** #456's scope listed them, and
  the PR description claimed the scope while omitting them. The review caught it.
