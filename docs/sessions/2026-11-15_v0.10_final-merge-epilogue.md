# Session 2026-11-15: the epilogue on the final merge (#427 part 1), and #434

## Context

to keep going with #427. #427 is several PRs:
- part 1: the epilogue on the final merge, the linear operator under WS and IS, and the
  fused-operation matrix test;

- part 3: the RTL contracts.

This is part 1.

## Decisions

1. **The program states the final merge.** A call into an L2 accumulator that carries `via`
   stages, all `@ combiner`, is the tile's last. The walker refuses any call into the tile
   after it. A level cannot tell which merge is last without lookahead. Holding each tile's
   last drain back until the next call or the store would delay drains in program order, and
   would keep partials in the fabric that the array cannot hold. The generator writes the k
   loop's last block out on its own.
2. **Placements:**
   - `combiner` runs the epilogue on the merged value;
   - `bm.egress` puts it on the store's Writeback (WS only, where b[j] is fixed for the panel);
   - `unfused` keeps the second pass;
   - `fabric` is refused, because it would act on one partial.
   Under IS, `bm.egress` is refused: the row panel's store has no single b[j].
3. **IS keeps b[j] resident around each final call** (`resident b[j]; call ...; release b[j];`).
   That pattern livelocked L-CA (#434). After the fix it runs, and it holds one L3 slot where
   b's row panel would hold tiles-per-panel.

## Bug found and fixed: #434

The BlockMover's Release guard waited while `stage_reads_[tile] > 0`. That counted every stage
read scheduled so far, including those of the tile's next residency. The driver's window hands
the next row's merges over before this Release is due. Those merges cannot run until b[j] is
loaded again, and the Load waits for this Release.
- **Fix:** count stage reads scheduled and applied, and give each Release the count scheduled
  before it (`TileDescriptor::after_stage_reads`). The same pattern as `after_drains`.
- The output-stationary repro now completes in 868 cycles.
- #433 (re-accumulating a written tile) is a different livelock and still open.

## Wrong decisions

- I first worked around #434 by making b's whole row panel resident (`b[:]`). It still
  livelocked at sizes 48 and 64, because the cause was the guard, not the residency pattern.
  Bisecting the epilogue stages (relu only passes, add only fails) found it. Lesson: bisect
  before working around.
- The matrix test first asked the fabric for gelu, which its target does not run (add and relu
  only).
