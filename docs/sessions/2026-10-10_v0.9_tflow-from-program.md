## 1. Summary

The tile-flow debugger (#286) now records CSP programs. `kpu-run --program file.csp --tflow`
writes a **version-4** bundle from the program's L-T1 run:
- the ops are the program's actions;
- the residencies are its own L3 slots.

The checker, the viewer and the floorplan binder read it, and the T4 reference run now comes
from a program `kpu-csp-gen` writes. Version 3 remains the record of an L0 run until 4e.

## 2. Decisions

- **Version 4 keeps version 3's columns and changes what an op is.** An op is one action, and
  `"ops": "csp-actions"` says so. The viewer, the LOD pyramid and the binder needed only a version
  check and a kind table. A new schema would have meant rewriting all three for no new
  information.
- **Each action is one op.** A movement action is one transit (a Store is two chained legs), a
  Call is one compute, and a Release is an op with no interval. TF7's "an op's hops chain"
  then holds as written.
- **TF6 and TF9 are restated for programs, the rest kept.**
  - TF6: an accumulator lives in the fabric with no L3 slot, and a Feed reads L2 after the
    program released the L3 copy. "Every op touching a tile runs while it holds a slot" is
    therefore false for a correct program. The program's rule is that every transit into or
    out of L3 runs while its tile holds a slot.
  - TF9: a result reaches L3 by its Writeback, so that hop fills a slot.
- **The label is load-bearing.** A v4 bundle without `ops` is refused (exit 2). The self-test
  shows that reading one as v3 fails TF6: the rules really differ.
- **The L3 station's capacity is the program's L3,** its credit pool, not the machine's.

## 3. Found by the checker

The first v4 record of matmul 48³ failed TF5, with A tiles holding two L3 slots at cycle 0. In
the column-panel schedule, A's row panel is reloaded for every column panel. L-T1 let the
reload's Load take a fresh credit before the previous residency's Release had run, which a
tile's single L3 entry cannot do. L-CA's DMA already waits a held load out.

The interpreter now makes a Load, or an opening Writeback, also wait for the tile's previous
Release. The rule was only ever stated in the executor, and the record's invariant caught the
interpreter breaking it.

TF9 also failed on every C slot: version 3 counted only DMA arrivals and computes as fills.
That is the restatement described above, not a bug.

## 4. Verification

- **The three corpus programs and the T4 reference** (`kpu-csp-gen` matmul 512³/64 on T4, L-T1
  makespan 84,224) pass all nine invariants.
- **The v4 self-test:**
  - the clean bundle passes;
  - zero-length residencies fail TF6;
  - writebacks relabelled as drains fail TF9;
  - an unlabelled v4 is exit 2;
  - a v4 read as v3 fails TF6.
- **`test_tile_flow_record` v4,** on matmul, unfused linear and LU: one op per action; slots
  equal residencies; L3 capacity equals the program's; the record's peak equals L-T1's peak,
  within the program's L3; one slot per tile at a time; a compute per Call; two legs per Store;
  a read-back.
- **The viewer smoke test and T4 binding** pass on v4 bundles. The v3 tests are unchanged.

## 5. Wrong Decisions

- **I forgot that a version test used "4" as the newer, refused version.** The full suite caught
  it. The test now uses 5, and also asserts that an unlabelled version 4 is refused.

- **My first attempt to rerun the record check used `rm -rf` on a shell-variable path.** The
  safety check refused it, correctly. I wrote to fresh directories instead. Deleting scratch
  output is never worth a destructive command whose target an empty variable could change.
