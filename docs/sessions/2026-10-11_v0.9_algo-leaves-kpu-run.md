# v0.9 `--algo` Leaves kpu-run; the Corpus Becomes kpu-sim Traces (kpu-run-csp-programs Step 5)

**Date:** 2026-10-11
**Version:** v0.9
**Status:** Complete (step 5, the last step of the kpu-run-csp-programs plan)
**Tests:** 267/267, CLI tests included

## 1. Summary

#356 (step 4e) was merged. Step 5 removes the derivation flags and the device flags from
kpu-run, because kpu-run is the simulator: it runs a program and does not write one. The L0
golden corpus was written by `kpu-run --algo ... --emit-l0`, so its regeneration needed a new
home. That home is kpu-run itself, running the corpus's CSP programs and writing their traces.

## 2. Decisions

- **kpu-sim is the one source of an L0** (decided by the user, 2026-10-11).
  - An L0 is the trace of a CSP execution (ADR 0004 §4). A test reference is made by running
    the program in kpu-sim, checking that every level agrees with the trace, and checking the
    trace in.
  - kpu-run's CSP path gained `--emit-l0` (the trace, with inputs) and `--emit-l0-kernel`
    (structure only). Both are written only after the agreement, as `--emit-l0-result` already
    was. `CspReference` carries the trace.
- **The corpus was regenerated from its `.csp` programs**, on the inputs kpu-run synthesizes
  (exact eighths).
  - Matmul 48³ and LU 64 keep their op count (90 and 42). For matmul the only difference is the
    trace's source labels. For LU I confirmed only that the count matches.
  - Linear 64 went from 256 ops to 240.
  - The kernel is the trace of a new `matmul_32x32x32_t16.csp`, and still demands only reader
    1.0.0.
  - `test_l0_corpus` now checks each file against the trace kpu-sim produces today (byte for
    byte), and checks that executing the file equals executing that trace (bit for bit). Before,
    both checks were against `driver::derive`.
- **Refused by name, with where the job went:**
  - `--algo`, `--size`, `--tile`, `--act` (to `kpu-csp-gen`);
  - the device flags (to `--deploy`).
  - `--program` is required.
- **The L0 path** keeps `--fill-inputs`, `--deploy`, `--emit-l0`, `--emit-l0-result` and `--step`.
  It runs L-B, prints "L-B ran the oracle", and writes its result: there is nothing to compare an
  oracle against.
- **Left for later:** `driver::derive` is still a second L0 source, used by tests,
  `examples/characterize` and the platform tests. Retiring it is its own step, and I flagged it
  to the user.

## 3. Found in CI

- **The synthesized LU input was ill-conditioned, and the clang builds failed on it.** macOS and
  Ubuntu clang computed element 3774 of the factored A as 0.00863311; the recorded value was
  0.00862026. The miss was 1.3e-5 against a tolerance of 1.09e-5.
  - Cause: `fill_operand`'s diagonal is a +32 nudge, and a 64-wide row's off-diagonals (each up
    to 8.875) sum well past it. LU then pivots on near-ties, which a host's code generation can
    tip.
  - The old derivation fill was strongly dominant (off-diagonals within ±0.5, diagonal 4 to 8),
    which is why the old corpus never showed this.
  - Fix: `csp_inputs` makes a square operand the program reads and then updates in place
    (`inout`, read first; LU's A) strictly diagonally dominant. It adds 9 × cols + 8, an integer,
    so the input is still exact. `in` operands keep their values, so a matmul's arithmetic stays
    exact.
  - Evidence: on the new input the float factorization matches a double-precision one to 0.6%
    of the corpus tolerance at its worst element, about 170× headroom. No pivot is a near-tie, so
    the pivoting strategy no longer matters.
  - Local gcc and clang, at -O0 and at -O3 -march=native -ffp-contract=fast, all agreed on the
    old input too. So the failure needed CI's hosts to show, and the margin is the evidence that
    it is fixed.

## 4. Wrong decisions

- **I proposed a `kpu-l0-gen` executable for corpus regeneration**, as the recommended option.
  It would have been a second L0 generator, beside kpu-sim, and it would diverge. The user
  rejected it and asked why the divergence failure mode had not been analyzed. It had not been:
  I anchored on preserving the existing corpus bytes, and those were pre-ADR-0004 derivations.
  The question to ask before proposing a tool is whether it duplicates a responsibility the
  simulator already owns. Saved to memory as feedback.
- **Regenerating the corpus with new inputs without checking how well conditioned they were.**
  The old LU input had been made dominant on purpose, and the README says so. The new input
  passed locally and failed on other hosts, exactly the history the README records for the
  `* 0.1f` fill.
