# v0.9 Domain-Flow Debugger, Step 2: The Record (.dflow)

**Date:** 2026-10-15
**Version:** v0.9
**Status:** Complete (step 2 of 5, `docs/plans/domain-flow-debugger.md`, #363)
**Tests:** 291/291 (release); new: `test_domain_flow_record` (7 cases), `dflow_check_selftest` (23), and 15 CMake bundle tests

## 1. Summary

A CSP program's L-B run is now recorded as a `.dflow` bundle, one step per action:
- the CSP state transition of every action (step 1's fields);
- every L3 residency with its address, open and close;
- the program positions, interned;
- a per-depth iteration summary that covers the whole run even when the step detail is cut.

The record is written by the oracle's own run. `driver::csp_reference` gained an observer, and
`DomainFlowRecorder` is one, so nothing walks the program a second time to build it.
`kpu-run --dflow` writes it, and `tools/trace/dflow_check.py` checks the plan's invariants on it.

During the session, a preview of the step-3 viewer was published as an artifact from the reference
run's bundle (matmul 512³ in 64-tiles at L3 17), for the user's review. The viewer itself is
step 3 and is not in this PR.

## 3. Technical Decisions

- **Decision 1: an observer on the oracle's run, not a recorder that runs L-B itself.** Plan
  invariant 1 says the record is the run that produces `csp_reference`'s values and trace. A
  recorder driving its own `CspBehavioralStepper` would be a second run (bit-identical, but a
  second run). `CspObserver::step(emission, lb)` is called after each action is applied, and
  `refused(action, what)` before a refusal is rethrown. The test checks that observing changes
  neither the values (bit for bit) nor the trace.
- **Decision 2: residencies and the iteration summary are complete; only `steps.bin` is cut.** As
  the plan says, the limit bounds the file, not the work.
- **Decision 3: iteration rows by loop-prefix change.** An iteration at depth d is one value of the
  first d enclosing loops. A new action closes every open iteration from the first loop where its
  (line, value) differs, and opens the rest. Depth 0 is one row for the program, so the summary's
  completeness (loads, stores, actions) is checkable against the manifest's totals.
- **Decision 4: format deviations from the plan's §3.4, recorded in the plan.**
  - Occupancy and peaks are u32, not u16: DRAM alone can hold more than 65,535 tiles.
  - `dirty` is not a residency flag: it changes over a residency's life.
  - `tiles.bin` interns tile coordinates.
  - A retained residency's `close` is its Retain, with the retained flag.
- **Decision 5: the checker's D3 covers L3 only.** Residencies are L3's. L2 and fabric counts have
  no independent record to check against, so they are checked through D6 (the iteration peaks
  must equal the steps' peaks).
- **Decision 6: a static refusal writes no bundle.** kpu-run validates the program before running
  it, so a program the validator refuses never runs and there is nothing to record. The refusal
  path (a program that reaches L-B and is refused) is tested in C++ through `csp_reference`.

## 4. Issues Encountered

- **The refusal never reached the observer.** `csp_reference` counts the actions first, to decide
  whether to keep a trace, and that pass hit the walker's error and threw before the observed run
  began. Found by `test_domain_flow_record`. Fix: the counting pass stops at an error, and the
  observed run refuses the program again at its own action, where the observer sees it.

## 5. Wrong Decisions

- My first refusal handling assumed every refusal comes from the observed loop. I did not account
  for the counting pass in front of it. The C++ test caught it before the PR.
- The plan's step 2 lists `--dflow-values`. I moved values entirely to step 4 (as the plan's step 4
  describes) rather than add a flag that does nothing. Recorded in the plan.

## 6. Validation

- `test_domain_flow_record`, 7 cases:
  - observing the oracle changes no value and no trace;
  - every recorded step equals the L-B stepper's step (kind, tile, process, move, residency,
    flags, address, occupancy, position);
  - round trip;
  - the iteration counts (1 + 3 + 9 + 27 on matmul 48);
  - a step limit cuts only `steps.bin`;
  - a refused program is recorded up to its refusal (action 2, "line 6");
  - the reader refuses a wrong format or version.
- `dflow_check` passes on bundles for the three corpus programs, the retain and inherit chains, a
  cut run, and the reference run (3,968 actions, 640 residencies, 585 iterations).
- `test_dflow_check.py`: 23 cases (6 added on review: malformed manifests exit 2, out-of-range rows are reported, not a crash, and a cut bundle's positions are checked). The clean bundle passes, and is not vacuous (opens, closes,
  three loop depths). Each of D2, D3, D4, D5, D6, D8 and D9 fails on a bundle that breaks it, and
  an unknown version or a missing table exits 2.
- Full suite (release, `nice -n 19`, `-j 2` / `ctest -j 4`): 291 of 291 pass after the fix; the
  build has no warnings.
