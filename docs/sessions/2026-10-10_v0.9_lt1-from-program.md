# v0.9 L-T1 From the CSP Program (kpu-run-csp-programs Step 3)

**Date:** 2026-10-10
**Version:** v0.9
**Status:** Complete (step 3); step 4 (corpus + platform) next
**Tests:** test_csp_run 7/7 (one new case, L-T1 added to the others); new CLI test
kpu_run_csp_block_sequential; full suite in the PR

## 1. Summary

L-T1 now executes the CSP program. It makes one tile move per transaction, under **the
program's** L3 credits: a Load takes one, the program's Release returns it, and nothing is
inferred.

`kpu-run --program file.csp` runs L-B, L-T1 and L-CA, all bit-identical to the L0 oracle on
every operand. The L0-driven `TileTransactionExecutor` is untouched and still serves L0 files
until step 4.

## 2. Decisions

- **A new interpreter, not a retrofit.** `TileTransactionExecutor` is a readiness-driven event
  engine over L0 ops, with inferred residency woven through 1,000 lines. The program already
  carries what that engine infers, so the interpreter it needs is much smaller.
- **One pass in program order.** Every dependency of a CSP action points backwards in program
  order: its data was placed by an earlier action, and its credit was returned by an earlier
  Release. Each action's start is therefore the latest of:
  - its data being ready (a scoreboard per tile and channel);
  - a free lane of its process;
  - in-order issue within the process;
  - a free credit, for a Load or an opening Writeback.

  No event queue is needed, the schedule is deterministic, and the cost is O(actions).
- **The credit pool is the program's L3** (`machine flat(l3 = N)`): the program's declared
  machine, not the deployment's larger one.
- **Values are the behavioral interpreter's,** stepped in the same order, so L-T1 cannot
  disagree with L-B on values. Its job is time.
- **Costs are the descriptor's:** lanes and bytes per cycle per process, compute tiles and MACs
  per cycle. A Store has two legs, the BlockMover ejection and the DMA write. Vector-unit time is
  reported as unmodelled; it is L-CA's.

## 3. Found on the way

**The plan's "L-T1 peak L3 equals the validator's" was wrong.** The validator's peak is the
program's live set in program order, which L-B reproduces. In time, the DMA runs ahead whenever a
credit is free, exactly as at L-CA. Matmul 256³ on S1 has a live set of 17 and holds 117 of its
128 slots at once. The invariant is live set <= peak <= program L3, and the plan now says so.

## 4. Verification

- `test_csp_run`:
  - matmul (col and row) and linear (four placements) at L-B, L-T1 and L-CA: all bit-identical to
    the oracle;
  - L-T1's DRAM loads and stores equal the validator's;
  - L-T1's peak lies within [live set, program L3];
  - its makespan is identical across two runs;
  - LU at L-T1 loads 16 tiles, A once.
- **The credit test:** a k-streamed program with 3 slots and 8 Loads. Every Load after the third
  starts no earlier than the Release that freed its slot, there are credit stalls, and the values
  equal L-B's.
- **CLI:** LU at `--level block-sequential` on S1 reports its makespan and L3 peak, and is
  identical to the oracle.
- **Measured,** S1 matmul 256³ (csp-gen column-panel): L-T1 43,840 cycles, L-CA 117,887, both with
  576 loads. Uncalibrated; the first calibration data point for the program path.

## 5. Wrong Decisions

- **My plan asserted an invariant (peak = validator's) without checking what "peak" means at a
  timed level.** The first L-T1 run on S1 contradicted it. Lesson: an invariant stated across
  levels needs a reason it holds at each level, not just at the one I had measured.
