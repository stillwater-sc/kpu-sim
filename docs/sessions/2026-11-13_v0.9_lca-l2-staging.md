# v0.9 L-CA Executes L2 Staging (#399, L2 part)

**Date:** 2026-11-13
**Version:** v0.9
**Status:** Complete; resolves #399 with #418 (the L3 part). Banks are #417.
**Tests:** gcc, the full suite: 313/313. clang, the full suite: 312/312. New in
`test_csp_lca_place`: 2 test cases.

## 1. Summary

L-CA used to skip the staging Move, run each staged Feed as a fresh Move from L3 plus a Feed,
and treat an L2Release as nothing. Now the staging Move puts the copy in the program's L2 slot,
staged Feeds read it there, and the L2Release frees the slot once those Feeds are done. L-CA's
L2 slots hold the same tiles, in the same order, as the walker's and L-T1's.

Also this session: PR #418 (the L3 part) merged after one review fix. GitHub closed #399 on that
merge, because the PR text said a later PR "resolves #399". I reopened it.

## 3. Technical Decisions

- **Decision 1: the staged copy is program-held, as a loaded L3 residency is.**
  - **Choice:** the staging Move inserts one reference, Feeds marked `l2_held` do not consume it,
    and the L2Release drops it.
  - **Alternative:** seed the entry with one reference per Feed, so the last Feed frees it.
  - **Rationale:** the stream form has no lookahead: when the staging Move is pulled, the driver
    does not know how many Feeds will follow. The L2Release does.
- **Decision 2: the executor retires an L2Release, not a process.** No single process owns it:
  the Feeds may run on several streamers. The executor counts the tile's Feeds scheduled before
  the release and retires it, in the cycle its last Feed completes, as L-T1 does.
- **Decision 3: the program's L2 slots are reserved.** Unstaged Moves and Drains took any L2 slot
  round-robin, so an unstaged copy could carry a placed slot's number. They now use the slots
  above the program's `l2`.
- **Decision 4: a staging Move is never deduplicated** onto a copy already in L2, and waits until
  the tile's earlier copy has left. A staged copy lives in its own slot.
- **Decision 5: the test asserts the staging, not a speedup.** See §4.

## 4. Issues Encountered

- **Staging leaves L-CA's timing unchanged on the test program** (4400 cycles both ways). The
  unstaged program issues 128 Moves but L-CA transfers 80. The executor's dedup
  (`process_dedup_moves`, #61) completes the other 48 on A's copy while it is still in L2. So
  unstaged, L-CA already reuses L2 copies the program never staged; L-T1 charges all 128. The
  test asserts 80 transfers staged and prints the makespans. Whether that dedup should remain
  for placed programs is a question for the user.
- **Review (CodeRabbit, PR #419), three findings, all valid:**
  - An ordinary Move queued after a staging Move of the same tile could arrive first, by a dedup
    onto another copy, and open the staged Feeds' gate (`after_moves`) before the staged copy was
    in its slot. Now an unstaged Move waits behind a queued staging Move of its tile.
  - `retire_l2_releases` matched the tile alone, so an L2Release with no Feeds could retire
    another L2 copy of the tile. Now it carries the staging's slot and turn, and retires only
    that copy, once that slot's claim for that turn is the tile's.
  - The driver's L2-size check threw; `csp_level_supported` now refuses the program, so a
    multi-level run skips L-CA instead of aborting.
  Each fix has an executor-level test that fails without it.
- To confirm the tests check something, I made the driver drop the staged slot once: both new
  cases failed (17 assertions).
