## 1. Summary

L-CA now runs the three init forms that step 1 added at L-B and L-T1:

```
acc C[i, j] in fabric init D[i, j] { ... }   // C = A.B + D
acc C[i, j] in fabric init b[j] { ... }      // C = A.B + b, broadcast down the rows
acc C[i, j] in fabric init C[i, j] { ... }   // C += A.B
```

The init is one more edge stream at L-CA too: its Load, Move and Feed run on the executor's DMA,
BlockMover and Streamer as an operand's do. The accumulator's first call waits for that Feed and
starts from its values instead of zero. On a 32×32 matmul in 8×8 tiles (`kpu_s1`), every level
agrees with L-B to the bit (max abs 0) for all four forms. The compute fabric's busy cycles are
unchanged (320): the init adds no MACs.

Also this session: the review of #407 (step 1). The validator now checks an init's tile position, and
both the validator and the walker check a bias row's column. #407 is merged.

## 3. Technical Decisions

- **Decision 1: the init is a field of the first call's spec, not a new compute.** The executor's
  accumulate path already starts a call from the fabric's accumulator. The first call is the one
  place an init enters, so the fed tile becomes its dependency and its starting value. A separate
  "seed" compute would occupy a compute tile and add a fill for no work.
- **Decision 2: the init is not a k-slice.** `compute_macs` skips it. The fabric's busy cycles are
  the no-init program's, and the init costs only its stream's time. That matches L-T1, where the
  init's Feed overlaps the first k step's operand streams.
- **Decision 3: an init's matrix is tagged, as a vector is** (MatrixID::A, tk = 1 + its index). The
  executor has three matrix ids. `csp_level_supported` admits another matrix only when nothing
  but an init reads it, so a program computing on D is still refused with the old reason.
- **Decision 4: inout C enters DRAM at its first Load,** if no Store wrote the tile before. The
  driver used to leave C out of DRAM, so that an output nobody stored reads as zeros. That still
  holds for `out` C.
- **Decision 5: the accumulator's credit is not modelled here.** The plan tied step 2 to "the
  accumulator's credit (#387)". L-CA's executor has no accumulator slots. ACQUIRE on a C tile's
  first K step and SIGNAL on its last are #387's, a tracking issue with no code planned yet. The
  plan's checklist row now says so.
