# v0.9 CSP Programs on the Platform, and a CSP Corpus (kpu-run-csp-programs Step 4a)

**Date:** 2026-10-10
**Version:** v0.9
**Status:** Complete (4a); 4b-4e planned (`docs/plans/kpu-run-csp-programs.md` step 4)
**Tests:** test_csp_corpus 3/3 (new); test_virtual_platform's class-closing test extended for
`schedule`; new CLI test kpu_run_csp_emit_result; full suite in the PR

## 1. Summary

Step 4 as planned ("the corpus and the platform, and retire the L0 path of L-T1") turned out to
cut through four working subsystems: orchestration, the tile-flow debugger, stepping and the
timeline, and characterization. I raised it, and the architect agreed to split the step. 4a does
the corpus and the platform; 4b-4e move each consumer, and the executor retires last.

4a:
- the canonical text of a program (`lang::format`);
- CSP programs on `VirtualPlatform`, with a run identity;
- `kpu-run`'s `.csp` path through the platform;
- a three-program CSP corpus run at every level on S1.

## 2. Decisions

- **A program's identity is its canonical text.** The canonical text has the program's
  structure in one layout:
  - no comments;
  - constant subexpressions folded;
  - parentheses only where precedence needs them.

  The language had only an IR printer, which loses the loops, so a formatter was needed.
- **A CSP run on the platform is a pure function** of (program, inputs, deployment, level,
  schedule). It does not write state back the way L0 runs do. Cross-run residency belongs to
  orchestration (4d), where it will be written in the program.
- **`schedule` joins `RunIdentity`**, compared and rendered. L-CA's window changes the
  makespan, so two runs differing only in it are different runs. The class-closing test's
  structured binding forced the update, as designed.
- **Without `--deploy`, placement is not checked.** A `.csp` run then uses the default device;
  values do not depend on placement, and L-CA (which needs a deployment) is skipped with its
  reason. This keeps step 2's behaviour.
- **The corpus reuses the L0 inputs and results** for matmul and LU, which csp-gen writes in the
  derivation's op order. Linear gets its own pair. Two claims as in the L0 corpus: tolerance
  across machines, bit-exactness to the oracle on one machine.

## 3. Found on the way

- **The canonical form must fold constants.** The first identity test respelled `0..3` as
  `(0)..(1 + 2)`, and the formatter kept the expression. That is a different spelling of the same
  program, so constant subexpressions now fold.

## 4. Verification

- `test_csp_corpus`:
  - the three programs at L-B, L-T1 and L-CA through the platform: within tolerance of the
    recorded results, and bit-identical to their oracles;
  - LU's L-CA refusal reason;
  - one program spelled two ways has one identity and one makespan;
  - a different window is a different run;
  - different inputs change the snapshot digest, not the program digest;
  - the formatter is a fixed point, compiles to the same actions, and keeps `a - (b - c)`.
- `test_virtual_platform`: `schedule` is compared and rendered.
- CLI: `kpu_run_csp_emit_result` prints a run id with `schedule:window=256` and writes the
  result after agreement. Existing CSP CLI tests use the moved corpus programs.

## 5. Wrong Decisions

- **The plan's step 4 bundled "retire the L0 L-T1 path" with the corpus** without counting its
  users. The survey found four subsystems. Lesson: before planning to retire something, list its
  users. A grep for the type took one command.
