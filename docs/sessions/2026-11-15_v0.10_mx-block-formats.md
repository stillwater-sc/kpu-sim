# Session 2026-11-15: the Combiner's MX block-format conversion (#427 part 2a)

## Context

#427 part 1 merged as #435. This is part 2a:
- Universal is bumped from v3.91 to v5.17.0, for its MX block formats;
- the Combiner converts results into MXINT8 and MXFP8 (esg#68: MXINT8 first, then MXFP8).

Part 2b is requantization (int32 -> int8, with rounding and saturation). It changes a result's
number system on its way into L2, which needs typed-output plumbing through the language and
every level, so it is a separate PR.

## Decisions

1. **Universal v5.17.0**, not v3.97. Both have `mxint8` and `mxfp8`, but v5.17.0's `mxfp8` is
   `e4m3_saturating`, which matches OCP's saturating conversion. kpu-sim uses three Universal
   headers (`cfloat`, `bfloat16`, `integer`), and the suite passes unchanged on v5.17.0.
2. **The conversion is a tile-context stage**, `mxint8 @ <place>` or `mxfp8 @ <place>`.
   - It is the context's last stage (esg#68's order: bias, scale, activation, format).
   - It runs on the Combiner or at bm.egress, never in the fabric.
   - A target unit's `ops` list names the formats it runs.
3. **Values, not storage.** The result keeps fp32 words holding the values the format
   represents: quantize, then dequantize, in runs of 32 row-major elements per tile. Modelling
   the stored format itself (a byte per element and a scale per block) in DRAM bytes and L2
   footprint is left for later. `numeric::block_bytes` gives the size for when it lands.
4. **The trace records `BLOCK_CONVERT`** (opset 1.6, `format=`), so the replay reproduces the
   conversion bit for bit.

## Upstream defects found (stillwater-sc/universal#2083)

Universal v5.17.0's mxfloat:
- **`mxint8` saturates each block's largest element.** `max_elem_exponent<int8_t>` is 7; an
  int8 code's emax is 6. So [100, 1.5, 2.5, -3.25] reads back as [63.5, 1.5, 2.5, -3.5].
- **`mxint8` rounds ties away from zero** (`std::round`). OCP rounds to nearest even.
- **`max_elem_exponent`'s explicit specializations are not `inline`.** A second translation
  unit including `mxfloat.hpp` fails to link.

**Decision:** MXFP8 goes through Universal's `mxfp8`, which checked correct here. MXINT8 is
converted per OCP MX v1.0 in `numeric.cpp` (the one Universal translation unit) until #2083 is
fixed: scale `2^(floor(log2 amax) - 6)`, codes rounded to nearest even and clamped to
[-128, 127]. The test does not include Universal, because of the link defect, and checks the
registry against values worked by hand.

## Wrong decisions

- **My first worked values for MXFP8 were wrong.** I expected 100 to survive. But 400 (100 at
  scale 2^-2) is not an e4m3 value: it lies midway between 384 and 416, and ties to even give
  384, so 96. Universal was right. Lesson: work the element grid out, not just the scale.
- **I first wrote the test against Universal's own `mxblock`,** which would have hidden the
  `mxint8` defect behind a self-consistent oracle. The hand-worked values found it.

## Validation

- `test_csp_block_format`, 4 cases:
  - the registry against hand-worked OCP values, idempotence, and the block bytes;
  - the language's rules;
  - every placement (OS and WS: combiner, bm.egress; IS: combiner) under both formats. Each
    one's result equals the same program without the conversion, converted tile by tile, at
    L-B, L-T1 and L-CA, bit for bit;
  - the `BLOCK_CONVERT` round trip.
- gcc: full suite, 325/325. clang: results in the PR.
