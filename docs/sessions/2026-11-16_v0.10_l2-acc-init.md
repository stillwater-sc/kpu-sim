# v0.10 An L2 Accumulator's Init, through the Combiner (#427)

**Date:** 2026-11-16
**Version:** v0.10
**Status:** in review (PR). #427 stays open.
**Tests:** see §5.

## 1. Summary

A fabric accumulator takes an init: `acc C in fabric init D`, a bias tile or row streamed in from
an edge. An L2 accumulator, which the WS and IS schedules use, refused one: "its first merge
overwrites its slot". So a WS or IS matmul could not compute C = A . B + D, and the generator
refused `--init` under those dataflows. Now the Combiner adds the init on each tile's first merge.

## 2. Technical Decisions

- **Decision 1: the Combiner adds the init on the first merge** (the user's choice, 2026-11-16).
  The slot is written with partial + X, the Combiner reading X from L3 as it reads a bias vector.
  - Alternative: the BlockMover preloads X into the partial's L2 slot, and every merge
    accumulates. It needs no new Combiner input, but a move cannot broadcast, so a bias row would
    not work.
- **Decision 2: the trace keeps the first merge an overwrite, then `MERGE_INIT`.** The replay
  checks an L2 accumulator's slot, and the first merge is the one that opens it, as an overwrite.
  So the add is a separate op after it: `MERGE_INIT` (opset 1.10), Y += X. X is a tile tiled as
  Y, or a vector broadcast down its rows, in Y's accumulator type. One op covers both shapes, and
  it runs before the final merge's epilogue when the first merge is also the last.
- **Decision 3: at the levels, the init is a stage.** `VeOp::Init` goes first on the first
  merge's Drain. The language has no spelling for it: the walker puts it there. Every level
  already handles a stage that reads a vector from L3:
  - L-B adds it to the merged value;
  - L-T1 counts the read for X's Release;
  - L-CA (`VectorStage::AddInit`) numbers, waits for and retires the read as it does an add's.
- **Decision 4: X must be resident at the `acc` statement**, in the validator and the walker
  alike, and still resident at the first merge (the walker). The shape and type checks are the
  fabric init's: the walker's are now one function (`check_init_shape`), shared by both kinds of
  accumulator.
- **Decision 5: `init C` (C += A . B) stays refused** for an L2 accumulator, with the reason. The
  walker refuses an L2 accumulator whose tile is resident in L3, and reading C into its own
  first merge needs that residency to hand over. A fabric accumulator does it already.

## 3. Issues Encountered

- **Review (CodeRabbit, PR #446): four findings, all valid.** The first three were gaps in the
  symbolic validator that the walker caught at run time. The fourth was a timing gap at L-T1.
  - **The init was checked only at the `acc` statement.** The validator kept no record of it, so
    it accepted an init released before the first merge. `Acc` now keeps the init, and the first
    call into the accumulator, as written, checks that the init is still resident.
  - **The init's tiles were not checked against the accumulator's.** `init D[1, 1]` for C[0, 0]
    passed. A tensor init must now name the same tiles as the accumulator, and a bias row Y's
    column.
  - **A slice counted as resident when one of its tiles was.** `covers()` takes its second
    argument as a single tile, so a resident D[0, 0] held D[0, :]. `contains()` is slice-aware: a
    slice dimension is inside only a slice.
  - **L-T1's Drain did not wait for the vectors its stages read.** The init, but also an add's
    bias and a per-channel scale's two: their Loads could finish after the Drain. The Drain, and
    the Writeback for its bm.egress stages, now wait for them (`stage_inputs`). No pinned makespan
    moved.
  - Tests: one per finding. The L-T1 one uses one slow DMA engine with D loaded last. Without the
    fix the Drain starts at cycle 2066, before D is loaded at 3072.

- **Second review (CodeRabbit, PR #446): three findings.**
  - **"Merged" was per accumulator, not per tile** (a follow-up on the first round). The first
    call marked the whole family merged. So an init released between a call into C[0, 0] and a
    second call statement into C[0, 1], whose first merge it is, still passed the validator. `Acc`
    now keeps the families each call has merged into, as written, and a call into tiles none of
    them covers checks the init. Test: the release between two calls is refused by both checkers.
  - **A tensor init on a vector accumulator** reached the tile comparison and read past the end of
    the vector's one dimension, which is undefined behavior. It is refused first ("a tensor init
    needs a tensor accumulator"). Test.
  - **An in-place Writeback did not consult the stages' reads of its tile.** Release and Retain
    do, through `stage_reads_`, and now the Writeback does too. The test does not reproduce a
    failure: the streamer's in-order issue already orders the scenario (D's Feed follows C's
    first-merge Drain), with or without the fix. The bound keeps the invariant if that order ever
    loosens, and the test pins it.

- **Third review (CodeRabbit, PR #446): two findings, both valid.**
  - **A first merge checked the whole init family**, where it reads one tile: X's tile in the
    same place (a tensor init) or X at the tile's column (a bias row), as the walker checks. A
    program that released `D[0, :]` and made `D[0, 1]` resident again before C[0, 1]'s first
    merge was refused. The whole family is still checked at the acc statement. Test.
  - **A loop body that may run zero times still marked its tiles merged.** `for k in 0..i`, with
    i = 0, merges nothing, so a later call is a first merge. `loop()` now forgets a body's merges
    when it may not run. A merge over the loop's variable stands past the loop for the whole
    dimension only when the loop runs over exactly its tiles, from 0; otherwise it is forgotten.
    Forgetting is conservative: the later call checks its init again. It can refuse a program
    the walker accepts (a partial loop, then a re-merge after the init's release), never the
    reverse. Tests: CR's program is refused by both; a loop over all of C's columns, then the
    init's release and a re-merge, is accepted by both.
  - The three new cases fail without the fix (3 assertions) and pass with it.

- **A missed finding from the second review: L2-stall accounting.** The Drain applied its stages'
  inputs (the init's Load) after the L2 credit comparison. So a credit that arrived before the init
  was counted as an L2 stall (`l2_bound`, `l2_wait_cycles`, the record's `l2_wait`), though the init
  decided the start. The stage inputs now come first. The Drain's timing is unchanged, since `max`
  is order-free; the accounting and the slot's open time are what change. Its test does not
  reproduce a failure: the streamer's in-order issue frees the previous accumulator's slot before
  the next partial is ready. It pins the invariant.

- **CI's `-Werror` build failed on files this PR does not touch.** The sccache backend was down, so
  every file compiled fresh for the first time in a while. Earlier runs had replayed cached
  results, which hid three warnings that clang 21.1.8 and gcc 15.2 raise:
  - clang `-Wunused-private-field`: three ids in `memory_orchestrator_integration.hpp`, set and
    never read. Marked `[[maybe_unused]]`.
  - gcc `-Wmaybe-uninitialized`: `StageGroup::type` in `schedule_generator.cpp`. Value-initialized.
  - gcc `-Warray-bounds`: `other.back()` in `test_virtual_platform.cpp`, on a vector gcc cannot
    prove non-empty. Guarded.
  `main` has the same latent break, and it shows on its next uncached build. Found with the
  `release-werror` preset locally, under both compilers, with `-k 0` to list every error at once.
- **#446 sat an hour with no CI.** `main` moved (#451 and #452 touched CHANGELOG.md), the PR
  conflicted, and GitHub runs no `pull_request` workflow on a conflicting PR. The watcher counted a
  snyk status as CI and reported SETTLED; the hand check of the merge rule caught it. The watcher
  now exits CONFLICT and NO_CI, and counts only check runs as CI.

- **Fourth review: an init skipped the Combiner's op-set check.** Valid. The suggested fix
  (`combiner->count(VeOp::Init)`) would have refused every init: `init` is internal, and a
  deployment cannot list it (`parse_veop` does not know it). The Combiner adds the init to the
  partial, and L-CA runs it as `AddInit`, so the check is that the target's Combiner runs `add`.
  It sits at the acc statement in both the walker and the validator. Test: refused without `add`,
  and accepted with it, or without the init.

## 4. Wrong Decisions

- **The second review's fourth finding (the L2-stall accounting) got no reply in that round.** I
  replied to three, not four, and the merge rule (every finding replied to) caught it before the
  merge. Lesson: list a review's findings by id from the API, and tick each one off, rather than
  reading them from the review's prose.

## 5. Verification

```bash
build/tests/program/test_csp_acc_init
```

- WS and IS, x `init bias` and `init bias-row`, x fp32 and int8, at L-B, L-T1 and L-CA, checked
  against a reference computed in the test:
  - fp32: init + A . B, within the proximity bound, because the init joins the reduction at a
    different point;
  - int8: the plain int8 matmul plus the init, wrapped in int32, exactly.
- The trace: one `MERGE_INIT` per C tile, at opset 1.10.0. It is written, read back and replayed
  bit for bit.
- The refusals: an init that is not resident, or not in the accumulator's type, and the
  generator's `--init accumulate` under WS.
