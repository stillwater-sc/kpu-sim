# v0.9 The Linear Operator at L-CA: CSP-Language Step 3 (Timed Vector Units)

**Date:** 2026-10-09
**Version:** v0.9
**Status:** Complete (step 3); the CSP-language plan's steps 1-3 are done
**Tests:** test_csp_linear_lca 4/4 (new); test_csp_driver unchanged (9/9, identical cycles);
full suite in the PR

## 1. Summary

Step 3 times the tile context. A stage now runs on the vector unit of the site the program
placed it on, and the cycle-accurate executor:
- charges the stage's time against the move it rides on;
- applies its values as the move lands.

`CspDriver` runs the linear operator in every placement and unfused, bit-identical to the L0
reference.

The larger result was not the vector units. Running one tile through **two residencies** (the
unfused epilogue stores C, reads it back, writes it in place, and stores it again) exposed five
places where the executor matched a tile by id and took the wrong copy. Each is now ordered by
the program.

## 2. Decisions

- **A stage overlaps its move.** The move takes `max(transfer, ve_cycles)`, and the excess is
  recorded as the unit's *bound* cycles: the measure of whether the unit keeps up. `fabric`
  stages run before the drain, charge the compute tile, and run at `macs_per_cycle` elements per
  cycle.
- **Values are applied by the executor,** from the stage queue kept per tile in schedule order.
  This is the same per-tile FIFO in which a tile's drains, and separately its writebacks,
  complete. The element functions are L0's.
- **A vector operand is named `A` with `tk = 1 + index`.** The executor's `MatrixID` has three
  values, and 30 sites and the credit partitions depend on that. A CSP tile's `tk` is otherwise
  0, so the tag is unambiguous. The alternative, a fourth matrix id, was a much larger change for
  no modelling gain.
- **The ordering fixes apply only to CSP descriptors** (`TileDescriptor::ordered`, set by the
  driver). The generator path's semantics, and the existing characterization numbers, are
  untouched.
- **Chain publication was rewritten, not patched again.** 1c.2 had added a retraction on top of
  the "last call scheduled" rule. The unfused epilogue's computes on the same tile broke that
  rule outright: the chain's last call never looked last, and the drain waited forever. A chain
  now ends at its DRAIN, and publishes when the DRAIN is scheduled and its calls are done,
  whichever comes later.

## 3. The five ordering hazards

Each was found as a crash ("payload ... without source bytes") or a hang, by the unfused
program or by a windowed stream:

1. **Chain publication.** The drain waited for a "last call" that never came. Fixed by `chains_`.
2. **Feed vs. a drained copy.** The unfused add's Feed of C matched the accumulator's drained
   copy in L2, which was on its way to its writeback. A program Feed now waits for the tile's
   earlier Moves to arrive (`after_moves`).
3. **Move vs. the old residency.** The unfused phase's Move of C matched the accumulator's
   written-back copy, before its Store. A written residency's Release now enters the
   BlockMover's epochs and retires after its Store's ejection.
4. **RAW through DRAM.** The reload of C read DRAM before the store had retired.
   - A program Load now waits for the tile's earlier Stores, by `program_seq`.
   - Queue position was not enough, because the driver hands Loads over later than everything
     else. My first version deadlocked on exactly that.
5. **RAW in L3, and Writeback vs. a moved copy.**
   - The relu phase's Move of C left before the add phase's in-place Writeback had landed. Moves
     and ejections now wait for the tile's earlier Writebacks (`after_writebacks`).
   - A Writeback matched the copy the next Move had brought to L2. Writebacks now wait for the
     tile's earlier Drains (`after_drains`).

The common cause: a tag CAM answers "is a copy of tile T here?", but a program with reuse needs
"is *this* copy of T here?". Program order is the only thing that says which copy.

## 4. Verification

- The matmul driver's numbers are unchanged: 43,968 / 38,089, the L3 4/8/16 table, 9,985, and
  the full window table.
- On S1, linear 128^3/32^3 with 16-lane units, every placement is bit-identical to the reference:
  - fabric, str.drain and bm.egress, with relu;
  - unfused;
  - atan on the streamers;
  - gelu split between fabric and bm.egress.

  Stage time is exact: 16 tiles x 2 stages x 64 cycles = 2,048 per unit, and 32 in the fabric.
  Unfused moves exactly 2 x 16 x 4 KiB more DRAM bytes, and takes longer (22,643 vs 17,628
  cycles).
- Fused and unfused also stream bit-identically at windows 4 and 64.
- At 1 lane, `bm.egress` is bound by 31,424 cycles, and the makespan grows from 17,894 to
  44,167.
- A stage on a site with no unit is refused by the executor, even for a program compiled without
  a target.

## 5. Review (CodeRabbit, one finding, fixed)

- **`stage_cycles` accepted a NaN vector rate.** `per_cycle <= 0` is false for NaN, so a NaN
  rate, or one small enough to overflow the cycle count, reached an undefined double-to-integer
  conversion. The spec already rejects a non-finite rate, but the executor's config can be set
  directly. Fixed:
  - a zero rate still means "no vector unit";
  - a rate that is not finite and positive is refused (a negated check, so NaN fails);
  - a cycle count outside `Cycle`'s range is refused before conversion.

  A test covers NaN, a negative rate, infinity and 1e-300.

## 6. Wrong Decisions

- **I first ordered a Load after "stores ahead of it in the queue".** The driver enqueues Loads
  late, so a later Store sat ahead of it, and the run deadlocked. The order has to be the
  program's (`program_seq`), not the queue's.
- **I fixed the hazards one at a time, each time with a fresh trace.** That was slower than
  reasoning about the class up front. After the second hazard, the right question was "which
  consumers match by tile id?", which would have found all five at once.
- **Two awkward ternaries in my first test draft** chose between two program strings on a
  condition that was always true. I replaced them with the intended strings.
