## 1. Summary

The RTL's programs are Python command generators; kpu-sim's are `.csp`. kpu-sim now lowers a
CSP program to the RTL's tile command stream and writes it as JSON. The JSON carries:
- the commands, field for field as kpugen's `Command`;
- the L3 contents the host writes before the tile runs;
- L-B's results.

A reference executor in Python runs the stream the way the tile's controller does and checks the
results.

## 3. Technical Decisions

- **Decision 1: option 1, kpu-sim lowers to the RTL's commands.** The issue asked for a
  decision and recommended this option. The user was away and had asked me to work through the
  issue, so I took the recommendation and say so in the plan. It can be revisited.
- **Decision 2: what the RTL executes was read from kpugen.** Two read-only research passes over
  branes-ai/embodied-ai-soc-generator gave the command fields, opcodes, `sync` bits, chain bits,
  slot placement and the 4×4×4 stream that `isa/matmul.py` issues. The lowering's 4×4 output is
  checked against that stream command for command.
- **Decision 3: the host fills L3 once.**
  - **Choice:** the program's Loads and Stores are the host's (`l3_init`, `results`), and the
    lowering refuses a program that reuses an L3 slot.
  - **Rationale:** the RTL's tile commands do not load DRAM into L3. A host DMA stream is a later
    version.
- **Decision 4: a gemm call is LOAD A, LOAD B, COMPUTE.** kpu-sim's Moves and Feeds are not
  lowered one for one: the RTL's pair slot is taken and released per COMPUTE.
- **Decision 5: the executor is kpu-sim's reading of the RTL, not the RTL.** It makes the stream
  testable here: the slot protocol holds, and the results are L-B's. It does not replace running
  the RTL (generator#49).

## 4. Issues Encountered

- The first 8×8 program made A and B resident row by row inside the loops. kpu-run's validator
  could not prove `A[i, k]` resident and refused it. Making both whole operands resident
  (`resident A[:, :], B[:, :]`) is valid and suits a host that fills L3 once.
