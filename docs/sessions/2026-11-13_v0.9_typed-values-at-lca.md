## 1. Summary

L-CA now computes typed gemms. An int8 × int8 → int32 matmul matches L-B on every operand, bit for bit,
for every init form (none, bias, bias row, accumulate onto C) in both loop orders.

Also this session: PR #412 (step 1) went through two review rounds and was merged.
- Windows: MSVC's C4293 on a shift by 32 in an unused ternary arm. Fixed with `if constexpr`.
- CodeRabbit raised five findings, all valid, all fixed with tests except the `kpu-run` one:
  - a typed file without values must still demand reader 1.3.0;
  - `.l0` integers are written without the stream locale's digit grouping;
  - `encode` reduces modulo 2^N before its cast;
  - a tile context's `add()` vector must be fp32;
  - `kpu-run --inputs` refuses an operand whose type differs from the program's.

## 3. Technical Decisions

- **Decision 1: the executor gets the MAC as a function pointer in the spec.** The executor stays
  ignorant of the registry. The driver looks up `numeric::mac(in, acc)`, the same entry L-B uses,
  so the two levels compute the same bits by construction.
- **Decision 2: fp32 keeps the executor's own arithmetic.** Routing fp32 through `mac_fp32` would
  change the summation order: the executor adds each product into the output, while the reference
  kernel sums into a local first. That would change fp32 L-CA's bits for no gain in this step.
  fp32 L-CA answers to L-B within the tile bound, as before.
- **Decision 3: words never pass through a float.** The driver's `payload()` used to `push_back`
  floats, and the readback assigned them. Both now `memcpy` words. On x86-64 and AArch64, float
  copies keep their bits anyway, but x87 does not. The test makes the risk concrete: every C
  word is shaped as a signalling NaN.
- **Decision 4: a typed matmul refuses bias and activation.** The validator already refuses a typed
  result's tile context. The executor checks again rather than apply fp32 stages to words.

## 4. Issues Encountered

- My first signalling-NaN test also claimed the sums wrap past INT32_MAX. They cannot: the largest
  positive sNaN word is 0x7FBFFFFF, and the matmul adds at most 127² × 8. I dropped that claim and
  check the exact first value. The wrap is covered by the step 1 test.
- `kpu-csp-gen` at size 16 with `--l3 8` needs 9-10 slots. The end-to-end runs used `--l3 12`.

## 6. Known Limitation (recorded in the plan)

The timed levels size an element at 4 bytes: L-T1 uses the device's `element_bytes`, and L-CA's
driver multiplies by 4. So an int8 program's DRAM bytes and transfer times are an fp32 program's.
For example, a 16×16 int8 matmul moves 6144 bytes where the RTL would move about a quarter of
that. Sizing per operand from `NumberSystem::bits` is follow-up work, before the RTL timing
cross-check.
