# Session: the memory hierarchy's roles, and the transpose's placement

**Date:** 2026-11-18
**Version:** v0.10 (in progress)
**Issues:** #483 (its open question), #479 (the test set's plan)

## 1. Summary

The architect answered the plan's open question Q1, where a transpose happens on the data path,
and stated the design rule behind the answer. The rule is recorded as an architecture document,
`docs/01-architecture/memory-hierarchy-roles.md`. It is linked from the execution model and the
docs index, and the plan's Q1 and its operator table now cite it.

## 2. Technical Decisions (the architect's)

- **The roles.**
  - **L3 is holding memory:** reuse, and double buffering against DRAM's latency.
  - **L2 is performance:** the concurrency that feeds the fabric.
  - **L1 is the stream transformation:** parallel vector in, element-wise out.
- **L2's data is pre-arranged.** At a 1–2 GHz array consuming two vectors per clock, with a
  ~250 MHz L2 SRAM (up to 8 array clocks of latency), at least 16 requests must be in flight. A
  read stream with that much concurrency cannot transform its data.
- **Transforms happen in the BlockMover, as it writes L2.** The first is #483's transpose.

## 3. Issues Encountered

- **A gap the rule exposes.** L-CA's banked L2 charges its read latency once per transfer, so it
  effectively assumes unlimited requests in flight. The outstanding-request requirement is neither
  modelled nor checked, and the document records it as future work for #401's later slices.
