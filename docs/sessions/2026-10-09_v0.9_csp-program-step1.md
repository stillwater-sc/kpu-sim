# v0.9 The CSP Program as the Center of Tile Sequencing: Plan and Step 1

**Date:** 2026-10-09
**Version:** v0.9
**Status:** Complete (step 1); step 2 (L-CA driven by the CSP program on `kpu_s1`) next
**Tests:** test_csp_program 6/6; full suite in the PR

## 1. Summary

The architect asked why the CSP program was not involved in sequencing the system-schedule work.
There is no schedule without it, and executing it is what starts the tile and burst sequence.
The question was right:
- the cycle-level executor ran hand-written `ScheduleResult` generators, a second source of
  sequencing;
- ADR 0002 (§4, §5.1) already named that gap;
- the step-3 dispatcher (#340) paced the generator's list from outside, a third source.

The architect's hypothesis frames the fix. KPU tile sequencing is an MPI decomposition:
- **Level 1** addresses one flat L3 and one fat compute fabric, with inner loops collapsed into
  tile-function calls (a compute tile is a whole matmul engine).
- **Level 2** divides and conquers over distributed L3 and compute tiles (SUMMA for matmul).
- **Below L3,** the L2/L1 processes are the tile's decomposition into the fabric's streams.

The plan, `docs/plans/csp-program-tile-sequencing.md`, makes the CSP program the only source of
sequencing. Q1-Q6 were all decided as recommended. #340 is closed, and its finding is kept as the
plan's §1.2 and in the withdrawn step-3 session log. Step 1 builds the program's IR, its lowering
from L0, and a behavioral interpreter.

## 2. Decisions

- **The lowering decides residency, by Belady for the given order.** It is optimal for a fixed
  order (verified against a brute-force minimum), so reloads become a property of the order. A
  better order is the next plan's.
- **Release is an action.** A residency closes with an explicit Release after its last consumer,
  so the interpreter can refuse any read of a freed tile. "Residency is the program's" is checked,
  not asserted.
- **Two L0 styles, one lowering.** Matmul's L0 feeds through ports and the fabric accumulates
  from zero (as every existing level assumes). LU's L0 works in place, so its operands are
  delivered and its results written back dirty.
- **L2 and the fabric are transit channels at level 1.** Capacity decisions there belong below
  L3, in the tile function's own decomposition (step 6).

## 3. Verification

- Matmul 256³/32³ against 128 slots: 128 Loads, 1,024 Moves, 64 Stores, 8 consumers per input
  residency.
- Matmul 48³/16³, capacities 1 to 18: 54, 48, 42, 36, 30, 21 and 18 loads, each equal to the
  dynamic-programming optimum.
- LU 64²/16²: 16 loads unbounded, 51 with 3 slots. 2 slots is refused by name (a trailing update
  needs 3).
- L-B over the program is bit-identical to the L0 reference for matmul and LU, unbounded and
  tight.
- Moving a Release ahead of its tile's Move is caught ("the tile is not in l3").

## 4. Wrong Decisions

- **The system-schedule plan (2026-10-08) built on the generator path without naming ADR 0002's
  gap, and step 3 added a third source of sequencing.** The architect caught it. Lesson: before
  planning work that feeds an interpreter, check what program it interprets against the ADR.
- **My first negative test released a C writeback, which has no Load to precede.** Corrected to a
  loaded residency.
