## 3. Technical Decisions

### Decision 1: scikit-build-core over setuptools

**Choice:** Use scikit-build-core for Python wheel builds

**Alternatives Considered:**
- setuptools with cmake extension
- meson-python
- pybind11's native CMake integration

**Rationale:** scikit-build-core provides modern CMake integration with PEP 517 compliance, automatic dependency handling via FetchContent, and seamless integration with cibuildwheel for multi-platform builds.

**Files Modified:**
- `python/pyproject.toml`
- `python/CMakeLists.txt`

### Decision 2: Universal library include path (v3.91)

**Choice:** Set UNIVERSAL_INCLUDE_DIR to `${universal_SOURCE_DIR}/include/sw`

**Alternatives Considered:**
- Using `include/` directly (fails with v3.91)
- Patching Universal headers

**Rationale:** Universal v3.91 moved headers under `include/sw/`. Setting the include root to `include/sw` allows existing includes like `<universal/number/cfloat/cfloat.hpp>` to work without code changes.

**Files Modified:**
- `cmake/Dependencies.cmake`
- `python/CMakeLists.txt`

### Decision 3: MSVC /Zc:__cplusplus flag

**Choice:** Add `/Zc:__cplusplus` to MSVC compile options

**Alternatives Considered:**
- Stub types to bypass Universal (rejected by user)
- Preprocessor workarounds

**Rationale:** Without this flag, MSVC reports `__cplusplus` as 199711L regardless of actual standard, causing Universal's `bit_cast.hpp` to skip including `<bit>` at global scope, leading to namespace pollution when `<bit>` is included inside namespace blocks.

**Files Modified:**
- `CMakeLists.txt` (root)
- `python/CMakeLists.txt`

### Decision 4: Trace library for KPU_API symbols

**Choice:** Build kpu_trace_for_python with BUILDING_KPU_SIMULATOR defined

**Alternatives Considered:**
- Making trace functions header-only
- Removing KPU_API from trace headers

**Rationale:** The `KPU_API` macro expands to `__declspec(dllimport)` on MSVC without BUILDING_KPU_SIMULATOR. This causes linker errors for TraceEntry destructor and to_string functions. Compiling trace_entry.cpp with the define exports symbols correctly.

**Files Modified:**
- `python/CMakeLists.txt`

## 4. Issues Encountered

### Issue 1: Universal v3.91 header path change
- **Symptom:** `fatal error: universal/utility/compiler.hpp: No such file or directory`
- **Root cause:** Universal v3.91 moved headers from `include/` to `include/sw/`
- **Fix:** Set UNIVERSAL_INCLUDE_DIR to `include/sw`

### Issue 2: bfloat16 header rename
- **Symptom:** `fatal error: universal/number/bfloat/bfloat.hpp: No such file or directory`
- **Root cause:** Header renamed from `bfloat/bfloat.hpp` to `bfloat16/bfloat16.hpp`
- **Fix:** Updated include path in `universal_types.hpp`

### Issue 3: MSVC std::bit_cast not found
- **Symptom:** `'bit_cast': is not a member of 'std'` and `sw::universal::std` namespace created
- **Root cause:** MSVC doesn't report correct `__cplusplus` value without `/Zc:__cplusplus`
- **Fix:** Added `/Zc:__cplusplus` flag to MSVC builds

### Issue 4: DFX library not building
- **Symptom:** Linker errors for DFXParser::parse_json, dtype_to_string, opcode_to_string
- **Root cause:** EXISTS check for non-existent `dfx_executor.cpp` caused INTERFACE library
- **Fix:** Changed check to `dfx_parser.cpp`, the only DFX source file

### Issue 5: TraceEntry dllimport linker error
- **Symptom:** `unresolved external symbol "__declspec(dllimport) ... TraceEntry::~TraceEntry"`
- **Root cause:** Missing BUILDING_KPU_SIMULATOR define caused dllimport instead of dllexport
- **Fix:** Added kpu_trace_for_python library with the define

### Issue 6: Linux passes but Windows fails
- **Symptom:** Linux wheels built successfully despite missing DFX library
- **Root cause:** GCC allows shared libraries with unresolved symbols (deferred to runtime); MSVC requires all symbols resolved at link time
- **Lesson:** Linux wheels were actually broken - would crash at runtime calling parse_dfx_json()

## 5. Wrong Decisions

### Wrong Decision 1: Creating stub types for MSVC

**What was wrong:** Initially created float-based stub types for fp16_t, bf16_t, etc. when MSVC failed to compile Universal types.

**Why it was wrong:** This bypassed Universal's fundamental design for managing address alignment and storage format with BlockType. The user correctly pointed out that Universal is developed on Windows and has never had such issues in applications with millions of lines of code.

**Correction:** Investigated root cause and found the real issue was missing `/Zc:__cplusplus` flag.

**Lesson learned:** When a well-tested library fails on a specific platform, investigate compiler flags and configuration before assuming the library is broken. The problem is almost always in how we're using the library, not the library itself.

### Wrong Decision 2: Wrong EXISTS check for DFX sources

**What was wrong:** The original CMakeLists.txt checked for `dfx_executor.cpp` which doesn't exist.

**Why it was wrong:** This check was copied without verifying the actual source files in src/dfx/. Only `dfx_parser.cpp` exists.

**Correction:** Changed EXISTS check to `dfx_parser.cpp`.

**Lesson learned:** Always verify file existence before writing EXISTS checks. Use `ls` or glob to confirm actual file structure.
