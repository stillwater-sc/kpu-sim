## 1. Summary

`tools/visualization/domainflow/` holds the viewer for `.dflow` bundles: a static page that reads
a bundle folder or a bundle `pack.py` embeds. It shows the L-B run as domains in the program's
channels, one action per step:
- L3 as its addressed slots, grouped by bank;
- the program position, with the current line and loop indices;
- an iteration ribbon covering the whole run;
- an inspector with per-slot histories.

It grew from the preview published for review in step 2; the preview's artifact now runs this
viewer, packed with the reference run.

## 3. Technical Decisions

- **Decision 1: a DOM-free data layer, tested in Node.** The plan asks for a headless test that
  steps, residencies and the program position render. There is no browser or jsdom in the build.
  So decoding and every read the page renders from (`parse`, `step`, `position`, `slotAt`,
  navigation) live in `<script id="dflow-core">`, which the test runs in Node. The test compares
  its output at sample steps with the bundle read independently through `dflow_check.load`. A
  mutation (a released slot shown as held) fails it.
- **Decision 2: the slot at a step is found by binary search.** Residencies in one slot never
  overlap (D9) and are stored in open order, so each render costs O(slots x log residencies). That
  scales to cut bundles of very long runs, where a linear scan per frame would not.
- **Decision 3: 64-bit columns become `Float64Array`.** Indices stay below 2^53. A u64 none
  becomes -1, so the UI never handles BigInt.
- **Decision 4: the ribbon draws from `iteration.bin`.** That table is complete even when steps
  are cut, so the whole run's loop structure shows; the cut region is shaded, and clicking past it
  stops at the last recorded step.
- **Decision 5: follow `tileflow/`'s conventions.** Folder picker, `pack.py` with a 12 MB cap and
  exit 2 on a non-bundle, and a version check the test ties to what the writer writes.
