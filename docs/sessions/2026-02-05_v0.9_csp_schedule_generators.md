## 3. Technical Decisions

**Decision 1: INTERLEAVED_AB as Default Strategy**
- **Choice:** Default MatMul strategy is INTERLEAVED_AB (A-B-A-B tile ordering)
- **Alternatives Considered:** OUTPUT_STATIONARY (keeps C resident), BLOCKED_AB (all A then B)
- **Rationale:** Interleaved ordering prevents buffer monopolization and is proven
  livelock-safe. BLOCKED_AB can cause deadlock with limited credits.
- **Files:** `include/sw/kpu/timing/schedule/matmul_schedule_generator.hpp`

**Decision 2: Static Validation Before Execution**
- **Choice:** All schedules validated statically before execution
- **Alternatives Considered:** Runtime-only validation
- **Rationale:** Static validation catches issues early without simulation cost.
  Validation rules (VAL-001 through VAL-006) provide fast feedback.
- **Files:** `include/sw/kpu/timing/schedule/schedule_validator.hpp`

**Decision 3: Multi-Pass Algorithms for Reductions**
- **Choice:** Softmax uses 4 passes (max, exp, sum, normalize); LayerNorm uses 3 passes
- **Alternatives Considered:** Single-pass online algorithms
- **Rationale:** Multi-pass is numerically stable and maps well to credit-based dataflow
  where each pass can be independently scheduled.
- **Files:** `softmax_schedule_generator.hpp`, `layernorm_schedule_generator.hpp`

**Decision 4: Im2Col Transformation for Conv2D**
- **Choice:** Conv2D uses im2col to convert to MatMul
- **Alternatives Considered:** Direct convolution, Winograd
- **Rationale:** Im2col maps directly to the systolic array's MatMul capability and
  reuses the existing livelock-safe MatMul scheduling strategies.
- **Files:** `include/sw/kpu/timing/schedule/conv2d_schedule_generator.hpp`

**Decision 5: Header-Only Generators**
- **Choice:** All schedule generators are header-only
- **Alternatives Considered:** Separate .cpp implementations
- **Rationale:** Minimal build dependencies, easy integration, compile-time
  polymorphism via templates. Keeps timing model ISA-independent.
- **Files:** All schedule generator headers

## 4. Issues Encountered

**Issue 1: TagCAM `remove()` method not found**
- **Symptom:** Compilation error: `class sw::kpu::timing::TagCAM has no member named 'remove'`
- **Cause:** Test file used non-existent `remove()` method
- **Fix:** Changed to `invalidate()` which exists in the TagCAM interface

**Issue 2: ScheduleAnalysis interleaving detection incorrect**
- **Symptom:** Tests failed with max_consecutive_a=0 when it should have been higher
- **Cause:** Code reset `consecutive_a=0` before updating `max_consecutive_a` when
  switching from A to B matrix
- **Fix:** Restructured analysis to update max counts before resetting:
  ```cpp
  case isa::MatrixID::B:
      result.b_ops++;
      if (last_matrix == isa::MatrixID::B) {
          consecutive_b++;
      } else {
          // Update max BEFORE resetting
          if (consecutive_a > result.max_consecutive_a) {
              result.max_consecutive_a = consecutive_a;
          }
          consecutive_a = 0;
          consecutive_b = 1;
      }
      break;
  ```

**Issue 3: ConcurrentTimingExecutor bugs during schedule execution**
- **Symptom:** Livelock detection triggered incorrectly, credit pool errors
- **Cause:** Bugs in component processes from earlier phases (not Phase 4 code)
- **Status:** Documented for future work; schedule generation/validation works correctly

## 8. Key Features Implemented

1. **Livelock-Safe Scheduling**: Default INTERLEAVED_AB strategy alternates A and B
   operations to prevent buffer monopolization

2. **Static Validation Rules**:
   - VAL-001: Empty schedules
   - VAL-002: Incomplete tile operations
   - VAL-003: Non-interleaved schedules (warning)
   - VAL-004: Unbalanced A/B ratios (warning)
   - VAL-006: Operation ordering violations
   - VAL-LL1 to VAL-LL5: Livelock safety checks

3. **Schedule Analysis**: Detects interleaving patterns and consecutive operation
   runs for livelock risk assessment

4. **Multi-Pass Algorithms**:
   - Softmax: 4 passes (max, exp, sum, normalize)
   - LayerNorm: 3 passes (mean, variance, normalize+affine)
   - BatchNorm: 1 pass (inference) or 3 passes (training)
