## 1. Summary

Fixed two critical bugs in the CSP concurrent timing model execution:
1. CreditPool double-release overflow caused by TagCAM rejecting duplicate tile insertions
2. Resource utilization calculation overflow caused by aggregated stall cycles exceeding simulation duration

Both fixes enable successful execution of MatMul schedules through the ConcurrentTimingExecutor.

## 3. Technical Decisions

**Decision 1: Reference Counting in TagCAM for Tile Reuse**
- **Choice:** Add `ref_count` field to TagCAMEntry, increment on duplicate insert, decrement on invalidate
- **Alternatives Considered:**
  - Deduplication at schedule level (breaks FEED semantics - same tile fed multiple times)
  - Deduplication at execution level (breaks dataflow when skipping operations)
- **Rationale:** Schedule generator emits all tile operations (A[ti,tk] for every tj).
  At runtime, TagCAM tracks how many times a tile is "in use". Only when ref_count
  reaches zero is the tile actually removed and credit released.
- **Files:** `include/sw/kpu/timing/tag_cam.hpp`

**Decision 2: Average Stalls Per Component for Utilization**
- **Choice:** Divide aggregated stalls by number of parallel components before subtracting
- **Alternatives Considered:**
  - Track actual busy cycles directly in each component (more invasive)
  - Cap at zero without averaging (inaccurate utilization)
- **Rationale:** With N parallel components over T cycles, max capacity is N×T.
  Aggregated stalls can exceed T when all N stall simultaneously. Averaging gives
  meaningful per-component utilization.
- **Files:** `include/sw/kpu/timing/concurrent_timing_executor.hpp`

## 4. Issues Encountered

**Issue 1: CreditPool::release() overflow - "pool already full"**
- **Symptom:** `std::overflow_error: CreditPool::release() called but pool is already full`
- **Root Cause:** MatMul schedule has tile reuse (A[ti,tk] loaded once, used n_tiles times).
  Multiple LOAD operations acquired credits, but TagCAM rejected duplicate insertions.
  When those in-flight LOADs completed and called insert() again, the credits were
  never properly acquired, causing credit imbalance.
- **Fix:** TagCAM now uses reference counting. Duplicate inserts increment ref_count
  instead of failing. Invalidate decrements ref_count, only removes when zero.

**Issue 2: Resource Utilization showing garbage values (4729934377874243584.0%)**
- **Symptom:** Utilization percentages showed nonsensical values
- **Root Cause:** Statistics calculation: `busy_cycles = total_cycles - aggregated_stalls`.
  With 4 DMA engines stalling 4566 total cycles over 966 simulation cycles, the
  subtraction underflows (unsigned integer).
- **Fix:** Compute average stalls per component type, cap subtraction at zero:
  ```cpp
  Cycle avg_dma_stalls = n_dma > 0 ? stats.dma_credit_stalls / n_dma : 0;
  stats.dma_busy_cycles = avg_dma_stalls < stats.total_cycles
                        ? stats.total_cycles - avg_dma_stalls : 0;
  ```

## 5. Wrong Decisions

**Wrong Decision 1: Deduplicate at Schedule Level**
- **What:** Initially tried removing duplicate LOAD operations in schedule generator
- **Why Wrong:** FEED operation consumes the tile. If A[ti,tk] is needed n_tiles times,
  we need n_tiles FEED operations. But we only have 1 LOAD. The schedule generator
  was correct to emit all operations.
- **Correction:** Added reference counting to TagCAM to handle tile reuse at runtime
- **Lesson:** Understand the full operation semantics before optimizing. LOAD acquires
  buffer space, FEED consumes the tile data. These are different resource flows.

**Wrong Decision 2: Skip Duplicate Operations at Execution Level**
- **What:** Tried checking `is_load_in_flight()` and skipping duplicate schedule_load()
- **Why Wrong:** Breaks the dataflow. If we skip scheduling a LOAD, the corresponding
  MOVE and FEED won't have the tile they expect.
- **Correction:** Let all operations proceed, but handle duplicates in TagCAM
- **Lesson:** CSP dataflow requires all operations to execute in sequence. Deduplication
  must happen at the resource tracking level, not the operation level.

## 10. Known Issues

1. **DMA utilization at 0%**: High credit stalls (4566 cycles across 4 engines for 966
   cycle simulation) cause average stalls per engine to exceed simulation duration.
   This indicates L3 buffer pressure. May need more L3 buffers or different scheduling.

2. **128×128×128 triggers livelock detection**: With 32 L3 buffers and 1024 tile operations,
   the resource constraints cause excessive stalling. Need either more buffers or
   smarter scheduling (e.g., prefetch limiting).

## 11. Continued Work: Credit Release and Tile Reuse

### Additional Fixes

**Issue 3: Credit release not conditional on reference count**
- **Symptom:** Double-release with 64 L3 buffers: "pool already full"
- **Root Cause:** BlockMover, Streamer, and DMA Store always released credits when
  invalidating tiles, regardless of ref_count. With tile reuse, multiple invalidations
  cause extra credit releases.
- **Fix:** Only release credit when `invalidate()` returns true (tile fully removed).
  Updated all components: dma_engine_process.hpp, block_mover_process.hpp, streamer_process.hpp

**Issue 4: DMA not detecting tiles already in L3**
- **Symptom:** DMA acquired credits for tiles already loaded
- **Fix:** DMA now checks TagCAM before acquiring credit. If tile is already in L3,
  just increment ref_count and skip the transfer.
- **Files:** dma_engine_process.hpp (added l2_tag_cam_ reference)

### Attempted Optimizations (Reverted)

**Attempted: Check if tile already in L2 before load/move**
- Added L2 TagCAM lookup in DMA and BlockMover to skip operations for tiles already downstream
- **Result:** Caused massive tag stalls (400K+ cycles) in 128×128×128
- **Root Cause:** When DMA skipped a load (tile in L2), corresponding MOVE waited forever
  for tile to appear in L3 (race condition between schedule processing and data flow)
- **Decision:** Reverted to simpler approach - only check L3 in DMA

### Additional CLI Options

Added `--l3-buffers <n>` and `--livelock <n>` to run_matmul for experimentation.

### Performance With Fixes

64×64×64 with 64 L3 buffers:
- Total cycles: 941
- FLOP/cycle: 557.16
- DMA util: 8.7%, BM util: 95.7%, STR util: 60.3%

### Known Limitation: Tile Reuse Semantics

With tile reuse, the first MOVE operation removes the tile from L3 (moved to L2).
Subsequent MOVE operations for the same tile find nothing in L3, causing tag stalls.

Proper tile reuse would require:
1. Keeping tiles in L3 until all consumers finish (copy semantics)
2. Or coordinating schedule to ensure tiles are consumed before reuse

Current workaround: Use enough L3 buffers (64+) to avoid credit pressure.

## 14. Chrome Trace Visualization Improvements

### Issue: Missing Resource Names in Trace

**Symptom:** Chrome trace displayed threads as anonymous numeric IDs, making it
impossible to distinguish DMA engines from BlockMovers from Streamers.

**Root Cause:** Chrome trace export only emitted event data without metadata events
for process and thread naming.

**Fix:** Added Chrome Trace metadata events:
- `process_name` for "KPU Concurrent Timing"
- `thread_name` for each component (DMA Channel 0, BlockMover 0, etc.)
- `thread_sort_index` for dataflow ordering

### Issue: Component ID Collision

**Symptom:** All component types used IDs 0-3, causing trace events to overlap.

**Fix:** Assigned distinct ID ranges:
- DMA engines: 0-N (sort_index 0+)
- BlockMovers: 100-10N (sort_index 10+)
- Row Streamers: 200-20N (sort_index 20+)
- Column Streamers: 210-21N (sort_index 30+)

### Thread Sort Order

Threads now appear in dataflow order (top to bottom):
1. DMA Channels (DRAM → L3)
2. BlockMovers (L3 → L2)
3. Row Streamers (L2 → L1, A matrix)
4. Column Streamers (L2 → L1, B matrix)

## 15. Grid Topology and Base Address Enhancements

### Component Naming with Grid Locations

**Request:** Human-readable component identification in trace with physical grid positions.

**Implementation:**
- Added `GridPosition` struct for 2D chip grid coordinates
- DMA engines: `MC{n}:CH{m}` format (e.g., "MC0:CH0", "MC1:CH1")
- BlockMovers: `L3(row,col):BM` format (e.g., "L3(0,0):BM", "L3(1,0):BM")
- Streamers: `CT(row,col):RowSTR` or `CT(row,col):ColSTR` format
- Process name includes topology: "KPU CSP Executor (2 MCs, 2x2 L3 tiles, 2x2 CTs)"

### Matrix Base Addresses

**Request:** Track and display matrix base addresses in DRAM for tile identification.

**Implementation:**
- Added `matrix_base_address` field to `TileDescriptor`
- Added `dram_address` and `matrix_base_address` to `TimingEvent`
- Updated trace JSON: `"tile":"A[0,0,0]","base":"0x1000","addr":"0x1400"`
- Set sensible defaults in run_matmul: A @ 0x1000, B @ 0x100000, C @ 0x200000

### Understanding DMA Behavior at Cycle 0

**User question:** Why do 8 DMA requests start at timestamp 0?

**Answer:** Each DMA "Channel" is actually a DMA engine with `queue_depth=8`, allowing
8 concurrent in-flight transfers. With 64 L3 buffers (ample credits), all 8 slots
issue immediately at cycle 0. This is correct behavior - the trace shows:
- `DMA_LOAD_START` (instant events) - when loads are scheduled
- `DMA_LOAD_COMPLETE` (duration events) - 50-cycle transfers starting at ts:0

BlockMover and Streamer events at cycle 0 are `BM_STALL_TAG` and `STR_STALL_TAG`
(instant events showing they're waiting for tiles), not actual transfers.
