  The Architectural Bug

  The TransactionalProgramExecutor works (produces correct functional results and generates timing), but its timing is inaccurate due to:
  - Sequential instruction dispatch (no DMA parallelism)
  - Missing data dependencies (streamers starting before block movers)
  - No credit-based flow modeling

  Options

  Option A: Ship v0.8.x as-is, fix timing in v0.9.0
  - Tag v0.8.x with current (inaccurate) timing
  - v0.9.0 replaces TransactionalProgramExecutor internals with CSP model
  - Harness infrastructure already built will test v0.9.0

  Option B: Fix timing before v0.8.x release
  - Delay v0.8.x until CSP timing model is complete
  - Effectively merge v0.8.x and v0.9.0

  Option C: Deprecate TransactionalProgramExecutor timing
  - Keep functional execution
  - Mark timing output as "approximate" until v0.9.0
  - Document known limitation

  Recommendation

  Option A - The harness infrastructure and executor interface are complete and valuable. The timing inaccuracy is a known limitation that v0.9.0 will fix. We should:

  1. Tag current work as v0.8.5 with release notes documenting the timing limitation
  2. Proceed to v0.9.0 CSP timing model
  3. The harness infrastructure (DMAHarness, BlockMoverHarness, etc.) will be reused to test v0.9.0

  The harness components we built (credit pools, journey tracking, validation) are directly applicable to testing the CSP model.
