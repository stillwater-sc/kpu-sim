  The Real Latency Hiding Mechanism

  Jetson AGX Orin (Ampere architecture):
  - 16 SMs
  - Max 48-64 warps per SM (Ampere), so let's say ~512-1024 warps total
  - 2048 CUDA cores total (128 per SM)
  - 4 warp schedulers per SM → 64 warps can issue per cycle

  Key insight I missed: Warps don't do ONE FMA then wait 200 cycles. A well-optimized GEMM kernel:

  1. Load a tile into shared memory (memory access)
  2. Compute MANY FMAs on that tile (pure compute, no memory wait)
  3. Repeat

  For a 16×16 tile with K=16:
  - Load: 2 × 16 × 16 = 512 elements
  - Compute: 16 × 16 × 16 = 4096 FMAs
  - Compute-to-memory ratio: 8:1

  With larger tiles (32×32), this ratio improves to 32:1 or better.

  Why 512 Warps is Enough

  The 200-cycle memory latency only matters during the load phase. If each warp does 100 FMAs per memory access:
  - 512 warps × 100 FMAs = 51,200 cycles of compute work buffered
  - That easily covers 200 cycles of memory latency

  The warp scheduler interleaves:
  - Warps doing compute (ready immediately)
  - Warps waiting for memory (stalled)

  As long as enough warps are in the compute phase, the cores stay busy.

  The Animation's Model is Pathological

  Our animation assumes 1 FMA per memory access (compute-to-memory ratio of 1:200). That's a worst-case scenario that would make ANY GPU crawl.

  Real GEMM has compute-to-memory ratios of 8:1 to 32:1, which is why 512 warps can sustain 2048 FMAs/cycle.
