Note on efficiency: The 5.6% efficiency reflects sequential wave execution in this functional simulation. In hardware, with 4 tiles computing in parallel per wave, efficiency would be 4× higher (~22%). Full parallel execution across all 16 tiles would approach theoretical peak.

> Can you elaborate on the note on efficiency? Are you saying that a functional simulator could not model parallelism, or this functional simulation is
not?

● Good question - let me clarify. It's the latter: this specific implementation doesn't model the parallelism, not that functional simulators can't.

  Looking at the current code structure:

  for (Size wave = 0; wave < NUM_WAVES; ++wave) {
      for (Size tile_in_wave = 0; tile_in_wave < TILES_PER_WAVE; ++tile_in_wave) {
          // Compute one C tile
          reference_matmul(...);

          // Add compute cycles for THIS tile
          for (Cycle c = 0; c < tile_compute_cycles; ++c) {
              kpu.step();
          }
      }
  }

The inner loop processes 4 tiles sequentially, adding ~511,000 cycles per tile. But in hardware with 4 compute tiles active per wave, those 4 tiles would execute in parallel - so the wave should only cost ~128,000 cycles, not ~511,000.

Two ways to fix this:

  1. Use ConcurrentExecutor: The simulator already has infrastructure for parallel execution. We could launch 4 parallel compute operations and wait for all to complete.
  2. Fix the timing model: Only advance the clock once per wave, not once per tile:

  for (Size wave = 0; wave < NUM_WAVES; ++wave) {
      for (Size tile_in_wave = 0; tile_in_wave < TILES_PER_WAVE; ++tile_in_wave) {
          reference_matmul(...);  // Functional compute (no timing)
      }
      // Advance clock once for the whole wave (parallel execution)
      for (Cycle c = 0; c < tile_compute_cycles; ++c) {
          kpu.step();
      }
  }

This would give ~22% efficiency (4 waves × 128k cycles = 512k compute cycles instead of 2M).
